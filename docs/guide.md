# SkinPulse 使用手册

安装、配置、每个功能的细节和取舍。项目简介和快速开始见 [README](../README.md)。

## 环境要求

- Python ≥ 3.12
- [uv](https://docs.astral.sh/uv/)（依赖管理与运行器）
- **macOS 或 Windows 10/11**。代码本身不分平台（路径用 `pathlib`，凭据走系统钥匙串 / 凭据管理器）；
  开机自启、崩溃重启、防睡眠两边各有一套，见下文「6. 开机自启」。作者自己的长期实例跑在 macOS 上。
- **不需要 Node**：看板前端（Vue）的构建产物已经提交在 `skinpulse/web/dist/`，拉代码就能用。只有改前端时
  才需要 Node（≥ 20，推荐 24），见下文「前端开发」。

## 快速开始

### 1. 安装依赖

```bash
uv sync
```

> **已知坑**：`uv sync` 曾经出现过"装出来的是残缺的可编辑安装"的情况（只生成了 dist-info，没有生成
> `.pth` 文件），表现为 `skinpulse` 包只能在项目根目录下被 import，换个目录跑 `uv run` 就
> `ModuleNotFoundError: No module named 'skinpulse'`。如果遇到这个问题，用下面的命令重装一次即可：
>
> ```bash
> uv sync --reinstall-package skinpulse
> ```

### 2. 生成配置文件

```bash
uv run python -m skinpulse init-config
```

会把 `settings.example.toml` 复制成 `settings.toml`（已在 `.gitignore` 中，不会被提交）。按需修改其中的
`[polling]`（轮询节奏）、`[alerts]`（告警门槛）、`[web]`（看板监听地址/端口）等分区，具体见下方
[轮询参数](#轮询参数)。

### 3. 配置手机推送（PushPlus → 微信）

告警以**微信消息**的形式送达，走 [PushPlus（推送加）](https://www.pushplus.plus)。微信本来就在手机上按时
收消息，不需要给任何 App 开后台或自启动权限。

1. 在 pushplus.plus 用微信扫码登录，拿一个 token（用户 token 或「消息 token」都行）。
2. 把 token 存进一个文本文件（文件名带 `token` 的 `.txt` 会被 `.gitignore` 排除），然后：

   ```bash
   uv run python -m skinpulse pushplus-token --from-file pushplus_token.txt
   ```

   它会往你微信发一条测试消息，成功后 token 存进系统钥匙串。**用完删掉那个文本文件。**
   Windows 上别在隐藏输入框里粘贴——Ctrl+V 可能进来一个看不见的控制字符，PushPlus 只会回 903。
   （这是 Windows 控制台的问题；macOS 终端直接粘贴应该没事，但还没实测验证过。）
3. 之后随时可以测试所有推送通道（**会真的发消息**，请自行执行）：

   ```bash
   uv run python -m skinpulse notify-test
   ```

**PushPlus 或 ntfy 返回成功都只代表它们的服务器收下了**，到没到手机以你实际收到为准——为什么强调这一点
见下文「推送走微信」一节。

<details><summary>可选：同时配置 ntfy 作兜底通道</summary>

ntfy 在国内**无法实时送达**（Google 推送不通，App 不常驻后台就收不到，而 ntfy.sh 只存 12 小时），所以只作
兜底。要配的话：在手机 ntfy App 订阅一个只有你知道的随机 topic（它相当于密码），然后把
`NTFY_TOPIC=<你的 topic>` 写进 `data/.env`（或存进系统钥匙串）。

</details>

### 4. 登录悠悠账号，同步求购单

**短信登录目前打不通**：悠悠有品 PC 端的登录接口会先要求过一道滑块验证码才肯发短信（`code 1110205`，
悠悠自己的错误码表里叫 `SLIDER`）。这道验证码没法用代码解决或绕过，所以

```bash
uv run python -m skinpulse login
```

现在会在"发送短信验证码"这一步直接失败，并提示改用下面的办法——命令本身还留着（万一以后这道验证码被
放开了），但目前走不通。

**实际可行的办法：把浏览器登录后的会话 token 复制进来**——用你自己的账号在浏览器里手动登录一次（人来
解滑块验证码），把浏览器保存下来的 token 交给本程序去用：

1. 用浏览器打开 <https://www.youpin898.com/> 并正常登录（短信验证码 + 滑块，全程人工操作）。
2. 打开开发者工具（F12）→ Network 面板，随便点开一个发往 `pc-api.youpin898.com` 的请求，在
   Headers → Request Headers 里找到 `authorization`，复制它的值——一个 `eyJ0eXA...` 开头、约 316
   字符的 JWT。

   > **不要用 `localStorage.getItem('LOGIN_TOKEN')`**：那是悠悠 App 内嵌网页的存储路径，桌面浏览器
   > 里取到的是 `null`。桌面端的 token 实际存在 cookie `uu_token` 里，但从请求头直接复制更省事。

   带不带开头的 `Bearer `、外面有没有多余的引号或空白都无所谓，下一步会自动清理（网页端自己发请求时
   是不带 `Bearer ` 前缀的，带不带服务端都认）。**连字段名一起复制进来也没关系**——`uu_token=eyJ...`
   （从 Application → Cookies 那栏复制的样子）、`authorization: eyJ...`（从 Headers 那栏复制的样子）
   都会被自动切掉前缀。
3. **最省事：在看板上粘贴**。打开看板「系统」页 → 悠悠账号卡片 → **「更新 token」**，把复制的值粘进去。
   会先拿它请求一次账号信息校验（一两秒），通过了才换上（正在跑的服务不用重启），并让下一轮监控马上开始
   （它开头会先同步求购单）；无效或暂时验证不了都不会保存，原来的 token 不受影响。每 5 秒最多试一次，连续失败 5 次锁 1 分钟。

   **或者用命令行**（服务没在跑、或者看板打不开时）：

   ```bash
   uv run python -m skinpulse set-token
   ```

   命令行换的 token 写进钥匙串，但正在跑的服务要重启（`scripts/macos/launchagent.sh restart`）才会用上；
   看板上换的立即生效。

   在提示符处粘贴刚才复制的值（输入不会回显）。命令会先拿这个 token 去请求账号信息**校验一遍**，
   校验通过了才会保存并同步——粘贴错了或者 token 已经失效会立刻告诉你，不会等到某次后台同步才发现。
   校验通过后会打印账号昵称和 userId，并像 `login` 一样立即同步一次求购单、打印同步到的张数。

   **token 很长**（约 300+ 字符的 JWT），而上面这个提示符是隐藏输入的——粘贴到底有没有完整落地，
   肉眼根本看不出来。更推荐的做法是先把复制到的值存进一个文本文件，再让命令直接读文件：

   ```bash
   uv run python -m skinpulse set-token --from-file path/to/token.txt
   ```

   文件内容允许带一个尾随换行、外面包一层引号、开头带 `Bearer `——规范化规则和交互式粘贴完全一样。
   规范化之后如果内容仍然带有空格/换行等空白字符（常见于从 devtools 里把折行显示的值直接复制出来），
   会被当作粘贴伪影直接拒绝，不会带着这种明显有问题的值去请求服务端。**校验通过、保存成功后命令会
   提醒一次：这个文件里还留着一份明文 token，用完请自己手动删掉**——程序不会替你删。

**这个 token 是账号的会话凭证，等同于登录态本身**：拿到它就能操作你的账号，所以永远不要把它分享给
别人、贴进聊天记录或截图，更不要提交进 git（`.gitignore` 已经拦截了 `*cookie*.txt` / `*token*.txt` /
`*.cookie` 这类常见的凭据抓取文件名，但文件名不规范时还是靠自己留意）。它会优先存进系统钥匙串
（Windows 凭据管理器 / macOS 钥匙串 / Linux Secret Service），钥匙串不可用时才退回明文写入
`data/.env`（同上，已在 `.gitignore` 中，不会被提交）。

**token 会过期**：token 是个 JWT，里面的 `exp` 就是到期时间——勾了"10天内免登录"时是签发后 10 天。
（早先文档写过「实测约 6 天」，那个结论证据不足：当时只观察到第 1 天有效、两周后无效，真实失效时间没测到。）
失效之后后台的监控轮次 / 心跳会开始报"登录已失效"，应用会在发现失效时立刻推送一条提醒，之后仍没换就每 24 小时
再推一条（写死，不可设置）——收到后重复上面 1–3 步、
存一个新 token 即可，不用重启程序。

**校验失败现在会分清两种情况，不再是一个笼统的失败**：

- **token 无效或已过期**：服务端明确拒绝（`LoginRequired`），消息会直接这么说——回浏览器重新登录一次，
  复制一个新 token 再试。
- **暂时无法验证**：校验请求本身没跑完（最常见的原因见下一段：YouPin 偶发的空响应），这跟 token 对不
  对是两回事，token **不会被保存**，消息也会明确写成"暂时无法验证"而不是"token 无效"。这种情况**直接
  重试一次通常就好**——命令内部已经会自动重试几次（约 3 次、间隔 2 秒左右，并在屏幕上说明正在重试、
  为什么重试，不会让人误以为程序卡住了），只有重试全部失败才会走到这条提示。

**排查提示：YouPin 在短时间内被频繁请求时，偶尔会直接回一个空响应体**（这个项目最早探测 API 时就见过，
大约每十次快速请求会遇到一次），这会被判成"限流"，和"token 无效"是完全不同的两件事——如果某个命令刚好
在这种情况下失败，等几秒钟再跑一遍即可，不必怀疑 token 本身有问题。

**如果 `set-token` 失败、但报错不是"token 无效或已过期"/"暂时无法验证"这种明确提示**（比如出现了
`youpin badjson: ...` 这样的信息）：这只说明校验请求没拿到能直接解析的 JSON 响应，不代表 token 一定是
错的——服务端某些接口的响应可能是加密/签名过的（响应头里带 `sk` 就是这个信号）。用同一个 token 再跑一次：

```bash
uv run python -m skinpulse probe-token
# 同样支持 --from-file path/to/token.txt
```

它会把这个 token 分别发给几个只读接口，打印每个接口的 HTTP 状态码、content-type、是否带 `sk` 响应头、
响应体长度，以及能解析出来的业务 code/msg（解析不出来就打印一小段截断摘要）；同时会打印一次"不带
token"时的基线结果作对照，帮你分清"这个 token 真被拒绝了"和"token 大概是好的、只是响应长得不一样"这
两种情况。**这份输出本身不含任何凭证**——不含 token、不含请求头、也不含 `uk`，可以放心整段贴进 bug
报告里。

### 多个悠悠号

一个服务可以同时盯几个悠悠号（建议不超过 4 个）。看板「系统」页 →「添加账号」，起个简称（推送和看板里用，最多 8 个字），粘贴那个号的 authorization，校验通过就开始同步。终端里是 `set-token --account 2`（第几个号）。

- **每个号要在自己的浏览器会话里登录**：同一个浏览器里切换账号会把原来那个号退出，它的 token 可能跟着失效。用另一个浏览器、无痕窗口，或者 Chrome 的「多个用户资料」，每个号一个。换 token 时也回到它自己那个资料里复制。
- 每轮按号依次同步，号与号之间隔 `[polling] account_gap_s` 秒（默认 10）。一个号登录失效或被限流，只停它自己；撞上风控（84104 之类）或机房拦截，所有号一起暂停。
- 有两个以上的号时，推送里每张单前面带 `[简称]`，登录失效的提醒标题写明是哪个号；看板总览右上角多一个账号切换（只影响总览和盈亏页；想写成「悠悠」「BUFF」而不是昵称，在系统页「参数设置 › 看板显示」里打开「账号写成平台名」），总览里主号以外的单带简称标签，同一个子队列里自己另一个号排在前面时会提示「前面是我的小号」。
- 系统页每个号一张卡片：更新 token、立即同步、改简称、停用。停用的号不再同步，它的单不算进总览，钥匙串里的 token 留着，再启用就接着用。**停用期间这个号的单如果成交了，SkinPulse 查不到**（不推送，「最近成交」里也没有）。
- 同一台电脑、同一个 IP 上登几个号，悠悠有没有可能当成关联账号，没有实测过。建议一个一个加，每加一个先跑几天。

### BUFF

也能盯你在 BUFF 上挂的求购单（[BUFF spec](superpowers/specs/2026-11-24-buff.md)）。对 BUFF 同样**只读**：只看你的求购、公开的求购队列和你的订单，不下单、不改价、不撤单。

1. 在 Chrome 里登录 BUFF，勾上「10 天内免登录」。
2. 开发者工具（F12）→ Application → Cookies → `buff.163.com`，复制 `session` 那一行的 Value。
3. 看板「系统」页 →「添加账号」→ 切到「BUFF」→ 粘贴 → 校验并添加。终端里是 `set-buff-cookie`（换 cookie：`set-buff-cookie --account N`）。

- **每 15 分钟一轮**（`[buff] round_interval_min`），和悠悠的轮次分开跑；同一个号两次请求至少隔 5 秒。一轮大约十几次请求。
- **名次是自己数的**：BUFF 不给名次。普通单只和普通单比，条件单只和条件完全相同的单比；价比你高的别的条件单另外提示「前面还有 N 张条件单」，不算进名次。
- BUFF 的单一律带 `[BUFF]`（或你起的简称）推送，点开跳 BUFF 商品页；推「升到第 1 名」「交易中」「求购成交」。价位建议、选品、简报、市价提醒不管 BUFF 的单。
- **成交是配出来的**：BUFF 的订单不带求购单号，单子消失后按「同一件饰品、同价、在挂单之后成交」去配订单。配不上的：交易中出现过就记「推测成交」（不推），否则当撤单。
- 撞到限流或验证码，这个 BUFF 号自动停 2 小时（`[buff] pause_hours`），推一条提醒，到时间自动恢复；悠悠照常。
- `session` 有效期未知（BUFF 未提供到期时间；登录页「10 天内免登录」只是参考）。失效时推「BUFF 登录已失效」，在系统页 BUFF 卡片上「更新 cookie」。
- 对不上悠悠饰品的 BUFF 单照样监控，只是没有详情页。
- BUFF 对脚本封号有先例。我们只读、慢、只给可能在前面的单数名次，但风险不是零。

### 5. 启动监控 + 看板

```bash
uv run python -m skinpulse run
```

已验证：该命令会同时启动后台调度器（监控轮询——每轮先同步一次账号求购单再抽样核对、心跳）和网页看板，默认监听
`http://127.0.0.1:8765`。用浏览器打开即可看到下面这些页面（均已验证可访问）：

- `/` 求购总览（新版前端，[看板改版 spec](superpowers/specs/2026-09-27-dashboard-redesign.md) 一期）：
  - 标题一句话回答「排得最好的是哪几张」（如「3 张求购排名第 2」），下面是离第 1 名最近的几张焦点卡片
    （离榜首还差多少、7 天排名走势）和三条提示（前 3 名的 7 天变化、今天名次升降、多少张难以成交）；
  - 全部求购表格：品类（大类 › 具体武器）/ 排名分段 / 隐藏难以成交的 / 搜索（条件记在网址里），表头排序；有「离第 1」「离市价」两列；
    「价格」一列把我的价、榜首价、悠悠在售画在同一条价格梯上，「离第 1」写差多少（按 ≤ 5% / ≤ 15% / 更多分档上色）；点行尾按钮展开这张单的
    7 天排名、价格位置（我的价 / 榜首 / 在售最低）和别处买盘；每 60 秒自动刷新，名次变了的行会闪一下；
  - 浅色 / 深色跟随系统，右上角可切换；⌘K 打开命令面板；系统开了「减少动态效果」时不播动画。
- `/?view=value` 总览的**价位视图**（右上角「排名 / 价位」切换）：每张单的一年分位、走势和相对大盘、7 天坏情况、
  按我的价成交和抢到第 1 以后的**扣费差价**，以及**建议**（考虑撤单 / 考虑降价 / 可以加价 / 保持 / 不评价，表头可筛选、
  展开行写出触发它的规则）；点提示卡按「一年低位 / 在跌且跑输大盘 / 难出手」筛选。见下面「价位」一节。
- `/item/<templateId>` 饰品详情（新版，二期）：我在这件饰品上的求购（多张单可切换）、全平台日线 K 线
  （MA7 / MA30、我的求购价虚线、1 月 / 3 月 / 1 年，「全部」是 2022-07 以来的周线（MA4 / MA13 周）、拖动滑块或
  双指捏合缩放）、「当前价位」卡片、各平台比价。
- `/analysis` 分析（新版，二期）：前 3 名张数和本周相比的变化、近 30 天每天收盘时前几名的张数（服务没跑的
  日子压成「停 N 天」）、现在的排名分布、今天升降最多的单。
- `/market` 大盘（新版，二期）：大盘指数和今天的涨跌、一年区间里的位置、最近 25 小时走势、一年日线，
  「全部」看 2023-07 以来的周线。
- ⌘K 命令面板可以按饰品名（简称、StatTrak、磨损）搜索我挂了单的饰品，直接进详情。
- `/system` 系统（新版，三期；旧的 `/status`、`/settings` 会跳到这里）：一句话说服务健不健康、四个通道
  （悠悠匿名 / 账号、PushPlus、ntfy）的状态、token 还剩几天和**「更新 token」**（在网页上粘贴，见上面
  「登录」一节）、排名核对的一致率、最近 10 条推送、最近 7 天简报、运行方式和数据库大小，以及可以折叠的
  **参数设置**（`[polling]`、`[alerts]`、`[brief]`，中文说明，保存后立即生效）。
- `/brief` 简报（新版，三期）：最近 30 天发了几条，每天一个节点（已发 / 补发 / 没发 / 无记录），点开看当天
  那张前 N 名表。见下面「每日简报」一节。

只想跑后台不开网页，加 `--no-web`：

```bash
uv run python -m skinpulse run --no-web
```

反过来，只开看板、不启动调度器（不监控、不发简报），加 `--web-only`。在另一台机器上看看板时用它，
两台都跑监控会各推一遍、对悠悠的请求量翻倍：

```bash
uv run python -m skinpulse run --web-only
```

按 `Ctrl+C` 停止。

### 6. 开机自启

#### macOS

用用户级 **LaunchAgent**（`~/Library/LaunchAgents`，不需要管理员权限；[ADR-0010](decisions/0010-macos-launchagent-caffeinate-on-ac.md)）：
登录后自动启动，崩溃或退出后 30 秒内自动拉起；**接着电源时 Mac 不会睡**（`caffeinate -s`，屏幕照常熄灭；
用电池或合盖时照常睡，睡着期间不监控）。

```bash
scripts/macos/launchagent.sh install     # 生成 plist 并启动；重复执行无害
scripts/macos/launchagent.sh status      # launchd 状态（state / pid / 上次退出码）+ launchd.log 最后 20 行
scripts/macos/launchagent.sh restart     # 拉了新代码之后：先 uv sync，再 restart
# 代码改了（合并、切分支、拉新代码）但服务没重启时，看板「系统」页标题会写「代码已更新，服务还没重启」，
# 旁边有「重启服务」按钮（只重启，不装依赖；依赖有变化时不给按钮，要先在终端 uv sync）
scripts/macos/launchagent.sh stop        # 停掉（下次登录会自动恢复；现在就要恢复用 start）
scripts/macos/launchagent.sh start
scripts/macos/launchagent.sh uninstall   # 停掉并删除 plist，以后登录也不再启动
```

- **install 之前**，先停掉终端里手动跑的 `skinpulse run`（Ctrl+C）。没停也不会出事：`run` 有单实例锁，
  launchd 拉起的那个抢不到锁就退出，每 30 秒重试一次，等手动的那个退出后接管。反过来，服务在跑时
  手动 `run` 会打印对方的 pid 并退出——要手动跑，先 `stop`。`sync`、`round`、`brief` 这些一次性命令不受影响。
- **日志**：完整日志照旧在 `data/logs/skinpulse.jsonl`（按大小轮转）；`data/logs/launchd.log` 只有警告、
  报错和崩溃时的 traceback。有手动实例占着锁时，launchd 那边每 30 秒会在这里记一行「已有一个 skinpulse run 在跑」。
- **一直起不来**（端口 8765 被占、拉代码后忘了 `uv sync`……）会表现为每 30 秒崩溃重启一次：`status` 里
  `runs` 一直涨、`last exit code` 不是 0，原因看 `launchd.log` 末尾。
- 服务一律从仓库根目录跑：锁文件和数据库都按 `settings.toml` 里的相对路径 `data_dir` 找。
- 凭据从 macOS 钥匙串读，和终端里跑时是同一个 python，正常不会弹框。如果 Homebrew 升级了 python，
  第一次读钥匙串可能弹「允许」框，选「始终允许」。

#### Windows

注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 里写一项 `SkinPulse`，登录时拉起一个**守护进程**
（`skinpulse supervise`，没有窗口），由它跑服务（[ADR-0021](decisions/0021-windows-autostart-supervisor.md)、
[ADR-0023](decisions/0023-windows-autostart-run-key.md)）：崩溃或退出后 30 秒内拉起；**接着电源时不睡**
（只拦系统睡眠，屏幕照常熄灭；用电池时照常睡）。不需要管理员。在 PowerShell 里、仓库根目录下运行：

```powershell
uv run python -m skinpulse service install     # 写入注册表 Run 键并马上启动；重复执行无害
uv run python -m skinpulse service status      # 自启状态、守护进程和服务在不在跑 + supervisor.log 最后 20 行
uv run python -m skinpulse service restart     # 拉了新代码之后：先 uv sync，再 restart
uv run python -m skinpulse service stop        # 停掉（下次登录会自动恢复；现在就要恢复用 start）
uv run python -m skinpulse service start
uv run python -m skinpulse service uninstall   # 停掉并删除自启项，以后登录也不再启动
```

- **在自己的终端里运行这些命令**。让 AI 编程助手（比如 Claude Code）替你跑 `service install` 时，它写的注册表
  可能是沙盒里隔离的一份，系统看不到，登录后就不会启动。
- **任务管理器「启动应用」里显示成 `pythonw.exe`**（不是 SkinPulse）；表头右键勾上「命令行」，带
  `skinpulse supervise` 的那一行就是它。可以在那里关掉；关掉后 `service status` 会提示「被关掉了」，
  重新 `service install` 或在那里打开都能恢复（任务管理器要关掉重开才会刷新）。
- **登录后没起来**：先看 `service status`。自启项指向的目录挪走了、`.venv` 没了，它会直接说；再看事件查看器
  「应用程序和服务日志 → Microsoft → Windows → Shell-Core → Operational」，登录时执行过的话有一条事件 9707，
  内容是 `Started execution of command '<仓库目录名>"'`（Windows 只记命令里最后一个反斜杠后面的部分）。
- 一个 Windows 用户只有一个 `SkinPulse` 自启项：在另一个 clone 里 `service install` 会把它改指过去。
- **从早期版本升级**：早期版本用的是「启动」文件夹里的 `SkinPulse.lnk`。升级后跑一次 `service install`（只
  `restart` 不会换），它会写上 Run 键、顺手删掉旧快捷方式；`start` / `restart` 发现旧快捷方式还在时也会提醒。
- `service install` / `uninstall` 报「改不了注册表」：多半是安全软件盯着 Run 键，在它里面放行后再跑一次。

- **凭据一律用 `--from-file`**：Windows 控制台的隐藏输入框里按 Ctrl+V，有时进来的是一个看不见的控制字符。
  悠悠 token 也可以服务起来以后在看板「系统」页里更新。
- **日志**：完整日志在 `data/logs/skinpulse.jsonl`；`data/logs/supervisor.log` 只有警告、报错、traceback 和
  守护进程自己的记录（什么时候拉起、退出码、电源状态变化）。
- **一直起不来**（端口被占、拉代码后忘了 `uv sync`……）会表现为每 30 秒重拉一次，10 分钟内连崩 10 次后
  改成 5 分钟一次；原因看 `supervisor.log` 末尾。
- 和 macOS 一样：`run` 有单实例锁，手动跑的和守护进程拉起的撞车时，后来的那个退出；服务一律从仓库根目录跑。
- **合盖**：Windows 默认合盖就睡，防睡眠拦不住。想合盖也监控，在「电源选项 → 选择关闭笔记本计算机盖的功能」里
  把「接通电源」改成「不采取任何操作」。
- 「重启服务」按钮在 Windows 上同样可用：服务以退出码 75 退出，守护进程 2 秒后重拉。

## 轮询参数

在 `settings.toml` 的 `[polling]` 分区调整，推荐范围（来自实测与同类工具经验，无官方阈值，建议按
看板「系统」页的通道状态逐步校准）：

| 键 | 含义 | 推荐范围 | 默认 |
|---|---|---|---|
| `request_interval_s` | 每次请求后的等待（±抖动） | 2–4 秒 | 3 |
| `round_interval_min` | 监控轮询周期 | 3–15 分钟 | 5 |
| `fast_lane_rank_threshold` | 抽样核对（见下）优先照顾的排名门槛：上报排名≤此值的单子每轮必抽 | 3–10 | 5 |
| `night_start_hour` / `night_end_hour` | 夜间静默窗口（本地时间，左闭右开；`start > end` 表示跨零点） | 按作息设置 | 0 / 8 |
| `night_multiplier` | 夜间窗口内，轮询周期乘以这个倍数（即该窗口内实际每 `round_interval_min × night_multiplier` 分钟才真正跑一轮） | 2–4 | 2.0 |
| `hourly_request_cap` | 每小时请求上限（保护账号/IP） | 200–400 | 300 |
| `verify_sample_size` | 每轮抽样几张单，用旧方法（公开队列+本地计算）核对一次 YouPin 上报的排名 | 3–10；0 关闭抽样核对 | 5 |
| `verify_enabled` | 是否启用抽样核对 | true/false | true |
| `deep_page_size` | 匿名那页装不下又没找到自己时，用认证请求深取的页大小；`0` 关闭兜底 | 100–400 | 200 |
| `sell_sample_size` | 每轮抽几张单刷新市场价（在售最低价） | 3–10；0 关闭 | 5 |

每轮监控现在只需一次认证请求（刷新全部求购单的 YouPin 上报排名）加上 `verify_sample_size` 次抽样核对，
而不是每张求购单各一次匿名请求，所以默认的 `round_interval_min` 已经从旧版本的 15 分钟降到 5 分钟；
如果想要更实时的排名，可以再往下调（同时留意 `hourly_request_cap` 的余量）。

`[alerts]` 分区里的 `confirm_rounds`（进了前 `enter_rank` 名需要连续确认几轮才推送，默认 2，避免抖动
误报；实时告警的 `enter_rank` 代码默认是 2，本机按 [ADR-0008](decisions/0008-realtime-alert-rank1-brief-top2.md)
改成了 1，即只在升到第 1 名时推送）也可以按需调到 1–3。看板「系统」页的**参数设置**可以在线改
`[polling]`、`[alerts]`、`[brief]` 三组（保存后立刻生效，简报的开关和时间也会重排，无需重启）；其他分区
（悠悠请求头、端口等）只能编辑 `settings.toml` 后重启 `run`。

### 告警用实时数字，不用悠悠上报的那个

**悠悠在「我的求购单」里给的 `rank` 和榜首价不是实时算的**，在有自动改价机器人的队列里会落后
几分钟。2026-09-21 实测，模板 108753：

```
悠悠说：第 2 名，榜首 ¥351
同一秒的公开队列：352（今天新挂） / 351 / 我的 158   →  实际第 3 名
```

背靠背连采三轮，差异分毫不动（所以不是采样间隔造成的）；把公开队列的原始 JSON 逐字段比对，
被漏掉那一行的条件字段与其它行完全相同（所以也不是"它带着我们看不见的条件"）。

这件事要紧，是因为告警本来整个建在这个值上，而滞后最严重的恰好是刀、高价皮肤这类有机器人
抢价的队列——也就是最值得抢的那些。你照着推送里的「榜首 351」去加价，实际要 352 才够。

所以在推送之前，会给**即将告警**的那几张单再拿公开队列现算一遍排名和榜首价，告警判断和推送
里的数字都用实时值（`confirm_with_live_queue`，默认开）。只核对「排名进了 `enter_rank` 带、
且还没处于告警中」的单——已经在告警中的单这轮不会再产生事件——所以每轮多打的请求是个位数，
上限由 `live_confirm_max` 兜住。核对失败绝不会变成"不告警"：拿不到实时值就退回悠悠上报的值。

### 推送走微信（PushPlus），ntfy 只做兜底

**2026-09-23 查实：ntfy 的推送从来没有实时到过手机。** 库里标成 `sent` 的 20 次推送，手机上只
看到 2 次。`sent` 的意思只是「ntfy.sh 收下了」——第二段「ntfy.sh → 手机」一直是断的：

- 国内 Google 推送（FCM）不通，ntfy App 要实时收就得常驻后台（自启动 + 后台运行权限）；
- **ntfy.sh 只把消息存 12 小时**，App 没在 12 小时内被打开，消息就永久没了。

所以主通道换成了 [PushPlus（推送加）](https://www.pushplus.plus)：告警以微信公众号消息的形式到达。
微信本来就在手机上按时收消息，不需要给任何新权限。

```bash
uv run python -m skinpulse pushplus-token   # 输入 token（不回显），会往你微信发一条测试消息
```

**Windows 上更推荐 `--from-file`**：把 token 存进一个文本文件，再
`pushplus-token --from-file 路径`，用完删掉那个文件。在不回显的输入框里按 Ctrl+V，有时进来的
不是剪贴板内容而是一个看不见的控制字符，你看不出来，PushPlus 只会回一句 903「token 不对」。
现在命令会直接拦下控制字符；真碰到 903 时会报出它实际收到的 token 位数，方便你对照网页。
这是 Windows 控制台粘贴的问题；macOS 终端里隐藏输入框直接粘贴应该没有这个问题，但还没验证过——
遇到问题同样可以用 `--from-file` 兜底。

几点说明：

- **两条通道同时发，任意一条收下就算发出去了**。每条通道在看板「系统」页上单独记健康状态，一条挂了
  另一条的成功盖不住它。
- **PushPlus 返回成功同样只代表它收下了**，不代表送到了微信——官方文档原话。查询真实送达状态要走
  它的「开放接口」（另外申请 secretKey 并绑 IP 白名单），暂时没接；设置时的测试消息靠你在微信里
  亲眼确认。
- **每条告警正文最后一行是「触发于 09-23 00:51」**——排名被观察到的那一刻。不管通道在路上耽搁多久，
  你看到的时间都是告警真正发生的时间。
- PushPlus 返回 `900`（账号被限制）时官方要求停止请求，约 2 天恢复，所以这个错误绝不重试；`905`
  是要求先完成实名认证。

### 推送失败不会再静默

从国内连 ntfy.sh 是条细管子，平时单次请求就要 5 秒左右。2026-09-22 夜里一条「第 2 名」告警
连续三次投递失败（`ConnectError`），而那三轮日志摘要写的都是 `alerts=0 errors=0`——只看摘要
完全不知道有告警没送到。现在：

- **每轮摘要多一个 `notify_failed=N`**，失败同时计入 `errors`；另外单独打一条 WARNING，只扫告警
  级别日志的人也不会漏掉。看板「系统」页的 ntfy 通道一直会记下最近一次 `publish_failed`。
- **连接阶段失败会重试两次**（间隔 3 秒、10 秒）。只重试 `ConnectError`/`ConnectTimeout`——这类
  请求一定没送到服务端，重试零风险。**读超时和服务端 5xx 不重试**：那时请求可能已经落地、只是
  响应没回来，重试会把同一条告警推两遍。
- 没送达的告警会把状态退回 NORMAL，满 `confirm_rounds` 轮后如果单子还在前 `enter_rank` 名就重新推送——
  这个机制一直都在，那三次失败之间正好间隔 30 分钟就是它在工作。

### 告警里的「别处买盘」

升到第 `enter_rank` 名不等于这件东西抢手——真实买盘可能在别的平台。所以要推送的那几张单会额外查一次
SteamDT，把 BUFF/C5 的最高求购价写进告警正文（饰品名已简写，见下）：

```
FN57 | 怒氓 (破损不堪)
第2名 | 我的价 18 | 最高价 320 | 市场价 354 | 别处买盘 317.5（BUFF/C5，比悠悠榜首低 1%）
```

依据是全量对账的结论：**悠悠的求购价比 BUFF/C5 中位数低 9.1%**，79% 的饰品都低。但那是总体
分布，不是每件都低——上面这件实测只低 1%。所以这一行给的是事实而不是结论，判断留给你。

没配 SteamDT key，或者查不到、配额用完了，就只是少这一行，**告警照发**。行情是加分，排名才是
本职。

### 市场价：「无人在售」和「还没查到」是两件事

看板的「市场价」列和告警里的市场价，取的是**悠悠在售最低价**（2026-09-21 用两张单对过：
FN57 \| 怒氓 (破损不堪) 给 354，和网页上完全一致）。

它是**抽样轮换刷新**的，不是每张单每轮都查——363 张单每轮各查一次就是 363 次请求，正是当初把
排名方案压垮的那个量级。每轮刷 `sell_sample_size` 张，优先照顾排名靠前的单（和抽样核对同一套
优先级），其余按「最久没刷过」轮换。所以某张单的市场价可能是前几轮查到的，鼠标悬停在格子上能
看到具体查询时间。

三种状态在看板上长得不一样，别混：

| 显示 | 含义 |
|---|---|
| `64.49` | 当时看到的最低在售价 |
| `无人在售` | **查过了**，市场上一件都没有在售 |
| `—` | 还没轮到这张单刷新，或者上次查失败了。价格未知 |

中间那一档是真实存在的：SSG 08（StatTrak™） \| 巨铁 (破损不堪) 连查三次都是 0 件在售，而同一
皮肤换个磨损有人挂。这时候「排名第 2」只是纸面排名——没有卖盘就没有成交。也**不能**拿别的磨损
的价格顶上来充数，同一皮肤不同磨损差价可以到几倍。

程序内部绝不会在价格缺失时填 0 顶上：「0 元在售」是个看起来合理、实际完全错误的值，而这个项目
已经因为价格字段静悄悄变成 0 吃过一次大亏（371 张单价格全存成 `0.00`，见 live-api-findings §4）。

### 差价过滤 `max_gap_ratio`：排名进了前 `enter_rank` 不代表值得抢

某张单进了前 `enter_rank` 名，不代表真的值得告警——如果对方最高价是我的价的 150 倍，理论上"第 2 名"，
实际抢不起，告警没有行动价值。这类噪音在真实数据里很好分辨：把账号里 371 张求购单的"最高价 / 我的价"
都算出来，当前排名 ≤ 2 的几张单里，比值要么是 1.01x / 2.00x（差距很小，加点钱就能抢到，确实该提醒），
要么直接跳到 150x——中间完全是空的，一眼就能分开"值得抢"和"陪跑"。而全部 371 张单的比值中位数是
2.24x，75 分位数 4.18x，37% 的单子比值 ≥ 3x。综合这两点，默认把 `max_gap_ratio` 设成 `3.0`：刚好卡在
中位数之上、能把最吵的那 150x 噪音过滤掉，又不会误伤两张真正接近的单子。

`[alerts]` 分区：

| 键 | 含义 | 默认 |
|---|---|---|
| `max_gap_ratio` | 离第 1 倍数：最高价 / 我的价达到或超过这个倍数时，即使排名进了前 `enter_rank` 名也不告警；`0` 关闭这个过滤 | 3.0 |
| `max_market_ratio` | 离市价倍数：市价 / 我的价达到这个倍数、**且**差价不低于 `min_market_gap` 时也不告警（见下一节）；`0` 关闭 | 2.0 |
| `min_market_gap` | 离市价差价（元）：差价低于这个数的不算离市价太远 | 20 |
| `confirm_with_live_queue` | 推送前用公开队列把即将告警的单现算一遍（见上一节） | true |
| `live_confirm_max` | 每轮最多核对几张 | 10 |

这个过滤发生在告警状态机**之前**（判断这张单本轮"够不够格"参与判断），而不是把已经产生的告警事件直接
丢掉——如果在事件产生之后才丢弃，订单会卡在 `ALERTING` 状态里出不来，之后即使差价缩小到能抢的程度，
`AlertEngine` 也会因为"已经在 ALERTING 了"而永远不再重新触发，等于一次静默丢单（这个项目已经在别的地方
踩过好几次这个坑）。现在的做法是：判定"不够格"的单子，直接当作没进前 `enter_rank` 名处理——连续确认轮数
清零，如果已经在 `ALERTING` 也退回 `NORMAL`；`last_rank` 仍然如实记录真实排名（看板要用）。这样一旦对方
撤单、或者自己把价格往上提，差价倍数一降下来，下一轮就能正常重新告警。

看板总览页「离第 1」列会在被这个过滤挡住的行上标「难成交」和倍数，方便直接从看板上看出
`max_gap_ratio` 挡住了哪些单子，照实际情况回头调整阈值，而不是凭记忆猜。日志里也会在每轮结束时打一条
INFO（`gap filter: N order(s) far from #1 …, M far from market … held back from alerting`），按轮汇总而不是逐单刷屏；
每轮的 `round:` 行里分别是 `gap_gated=` 和 `market_gated=`。

### 难以成交：离第 1 或离市价太远

只看「离第 1」有个漏洞：第 1 名的榜首价就是自己，比值永远是 1，所以 10 元求购、在售 4871 的纪念包照样
是「第 1 名」、照样推送。可卖家不会按 10 元卖给你。所以再加一把尺子——**离市价**：

- **市价**：悠悠在售最低；查过、没人在卖时用「别处买盘」（其他平台的最高求购）；两样都没有就判断不了，**不藏**。
- **离市价太远**：市价 ÷ 我的价 ≥ `max_market_ratio`（默认 2），**并且**市价 − 我的价 ≥ `min_market_gap`（默认 ¥20）。
  两个条件都要：7 元求购、在售 9.46 这种比例高但只差两块钱的不算；贵的饰品挂在市价下 10%～15% 是正常求购价，
  比例不够也不算。默认值来自 2026-11-25 的正式库：713 张里这条规则新增 55 张。

离第 1 或离市价太远，任一条成立就是「难以成交」：

- 不推「升到第 1 名」，不进每日简报（和差价过滤同一个机制，在状态机之前挡）；交易中、成交、市价提醒照推。
- 看板总览：「离市价」列写差价和倍数；「隐藏难以成交的」勾上就藏掉，不勾时这些行变暗，原因标在触发它的那一列；
  标题和焦点卡片只数可成交的单。
- 三个阈值都在系统页「参数设置 › 推送规则」里改，下一轮生效。

**为什么排名不再逐张单去公开队列算**：早期设计是每轮给每张求购单各发一次匿名请求、在公开队列里数出自己
的排名。第一次用真实账号（371 张求购单）跑起来才发现两件事：YouPin 自己的 `searchPurchaseOrderList`
接口其实直接把排名（`rank`）和当前最高价（`maxPurchasePrice`）算好放在每一行里了；而 371 张单按原设计
一轮要 18 分钟以上，比 15 分钟的轮询周期还长，round 根本跑不完。现在改成"以上报排名为准、每轮抽样几张
用旧方法核对"：看板「系统」页能看到最近抽样核对的次数、一致的次数，以及最近一次不一致（如果有）。

**`rank` 的语义已经查实：它是同条件子队列排名，不是全模板排名。** 2026-09-07 拿三张"磨损不限"的求购单
对照公开队列逐一验证，三次全部吻合：

| 模板 | 我的价 | 全表位次 | 同条件（不限）子队列位次 | 悠悠给的 `rank` |
|---|---|---|---|---|
| 1022 裹手 | 203 | 18 | **4** | 4 |
| 60677 暗影双匕 | 180 | 4 | **3** | 3 |
| 47829 九头蛇手套 | 170 | 11 | **6** | 6 |

`maxPurchasePrice`（看板"最高价"列）同样是**子队列**的榜首价而不是全表榜首：模板 1022 全表最高 332、
子队列最高 276，悠悠给的是 276。所以看板上的排名和最高价都可以直接按"同条件子队列"理解，跟本文开头那句
承诺是一回事。

这三张单的条件都是磨损"不限"，款式/异色/纹理那几维账号里没有对应的单子，还没验证过；抽样核对因此保留
着，当作语义万一变化时的哨兵，而不再是"等着回答一个未知问题"。

**匿名那一页只有 20 行，但登录后能翻页**。公开队列匿名调用是硬上限 20 条，`pageIndex`/`pageSize` 都被
忽略，`hasNext` 还会在后面明明还有的时候谎报 `false`。带上 token 之后两个参数才真的生效——2026-09-21
实测模板 101422（`total=347`）：匿名传 `pageSize=100` 仍返 20 条；登录后 `pageSize=100` 返 100 条、
`pageSize=400` 一次返回全部 347 条，`pageIndex=2` 与第 1 页单号零重叠、正好接在第 20 条之后。

所以「自己的单排在全表 20 名开外」不再是死角：匿名那一页装满了又没找到自己时，会用一次**认证**请求把
整个队列深取回来再算（`deep_page_size`，默认 200）。只在这种情况下才升级——认证请求是拿账号在换深度，
风控盯的正是账号。深取之后仍然找不到自己，那就是真的对不上（记成不一致），而不是「看不见」。

`deep_page_size = 0` 可以关掉兜底，退回老行为：这类单在「系统」页上计成**无法判定**，不计入不一致
——它说明的是"我们看不到"，不是"悠悠算错了"。

## 每日简报

每天 **00:00** 判定前一天（本地时间），出一张**前 2 名表**：前一天收盘时排在前 2 名的单（难以成交的不列：
榜首价 ≥ 我的价 × `max_gap_ratio`，或离市价太远，见「难以成交」一节），按名次、同名次按我的价从高到低排。和再前一天收盘相比，
**表里有单变了才推送**到微信（PushPlus 发成表格，ntfy 兜底发纯文本）；连续 7 天没发过，就发一行
「近 7 天前 2 名单没有变动（新进 / 名次 / 榜首价），监控在正常运行」。「离开前 2」不推送、也不列。
00:00 时电脑没开、服务没在跑的，服务下次启动如果在 `send_at` 之后 12 小时以内，会自动补判一次错过的那天
（同一天已有记录不会重发）；超过 12 小时就算了，交给下一个 00:00。

表的列是「名次 | 饰品 | 求购 | 榜首 | 在售 | 变动」，有变动的行加粗。纯文本一行长这样：

    第2名 | 廓尔喀刀(★ ST) | 人工染色 (久经) | 求购 158 | 榜首 248 | 在售 — | 🆕新进，榜首 249→248

- **变动**三种：`🆕新进`（新单，或原来不在前 2）、`名次 3→2`（原来就在前 2，名次变了）、`榜首 250→248`
  （榜首价变了；自己是第 1 名时不标，因为那就是自己的价）。在售价变了不算变动。
- **榜首**：自己是第 1 名时写「我」。
- **在售**：当天 23:50 价格快照（SteamDT，约 5 分钟）里的悠悠在售最低价；那天没拍到、没配 SteamDT key、
  或者没人在卖，都写「—」，不会写 0。表下最后一行写这些价格是什么时候拍的，比如
  「在售：09-22 23:50 悠悠价格快照」（白天手动跑过 `price-snapshot` 的话，这里就是白天的时间）；
  那天没拍到就写「在售：09-22 没有价格快照」。
- **饰品名简写**：磨损写崭新 / 略磨 / 久经 / 破损 / 战痕，`StatTrak™` 写 `ST`，全角括号改英文括号。
- 表太长时，微信按 16000 字节、ntfy 按 4000 字节整行截断，末尾写「另有 N 张未列出」；看板 `/brief` 里存的是全文。

简报列前几名由 `[brief] top_rank` 决定（默认 2），和实时告警的 `[alerts] enter_rank` 分开。

    uv run python -m skinpulse brief                       # 预览昨天的简报（不发）
    uv run python -m skinpulse brief --date 2026-09-22     # 预览指定日期
    uv run python -m skinpulse brief --date 2026-09-22 --send --force   # 真的发（已发过也重发）
    uv run python -m skinpulse price-snapshot              # 手动跑一次今天的价格快照（没有 --date：接口只给当前价，只能拍今天）

每天发没发、为什么没发，看板 `/brief` 页都有记录；00:00 服务没在跑、没有判定的日子显示「无记录」。时间、前几名、兜底天数在看板「系统」页的参数设置里改（或 `settings.toml` 的 `[brief]` 分区）。

## 价位（值不值得买，一期、二期）

目的是赚差价，所以回答的是：**按这个价买进来，扣完手续费、提现费、让价，再扛过 7 天交易保护期，还能剩多少**。
设计见 [价位 spec](superpowers/specs/2026-09-27-price-position.md)，为什么分三期见 [ADR-0014](decisions/0014-valuation-advice-three-phases.md)。
一期给描述；二期（2026-10-09）回测过之后加上**建议**，规则和回测结论见下面「建议」。

每天 **00:30**（`[valuation] run_at`）给活跃求购单的饰品取一次悠悠日线（SteamDT，每分钟最多 60 次，约 430 件
要 12 分钟左右），存进自己的库（`daily_bar`，SteamDT 的历史会变，自己存的才能复现），再结合前一晚 23:50 的价格
快照算出每件的：

- **一年里的位置**：一年收盘价里的分位（≤ 20% 叫一年低位）、一年最高 / 最低；
- **走势**：MA7 / MA30 的上升 / 横盘 / 下降，30 天涨跌和大盘比（差 3 个百分点以上叫跑赢 / 跑输）；
- **7 天坏情况**：过去一年里「7 天涨跌」最差的 10%；**波动**（EWMA）、**出手难易**（在售件数、买卖价差）；
- **扣费差价**：在售最低价 × 0.99（让价）× (1 − 交易手续费) × 0.99（提现），默认只按悠悠算（`[valuation] exit_platforms`，
  2026-11-23 起；写成 `["YOUPIN", "BUFF"]` 就两家各算一遍取到手多的），
  再和我的价、「榜首价 + 0.01」（抢到第 1）比。

手续费按真实成交核对过：悠悠 1%，BUFF 1.5%（2026-04-14 起统一），提现各 1%（`[valuation.fees]`、`withdraw_fee`）。
00:30 电脑睡着的，启动时 12 小时内会补算。不向悠悠发任何请求。

    uv run python -m skinpulse valuation                     # 估昨天（会真的请求 SteamDT）
    uv run python -m skinpulse valuation --date 2026-09-27 --dry-run   # 照常取数计算，不写库

**建议**（`[valuation] advice = true`）：按顺序判断，命中一条就停，每条都写出触发它的规则和数字。

1. **不评价**：交易中、条件单、日线不足、没有在售价；
2. **考虑撤单**：按我的价成交、碰上 7 天坏情况会亏；
3. **考虑降价**：坏情况下还赚，但不够目标差价 15% 或每件 ¥1（`target_margin`、`min_profit`），写出降到多少；
4. **可以加价**：不是第 1，加到「榜首 + 0.01」也没超过求购价上限，写出加到多少；
5. **保持**：其余。

只用回测通过的规则：「7 天坏情况」按第 10 百分位校准过；「在跌且跑输大盘」**没通过**，只是描述，不作撤单理由。
回测只读库、不请求任何外部接口，每季度重跑一次（[研究报告](research/2026-10-09-valuation-backtest.md)）：

    uv run python -m skinpulse backtest --out report.md                 # 默认 H2 从 2026-04-01 起
    uv run python -m skinpulse backtest --split 2026-07-01 --out r.md   # 重跑时把分界往后挪

同步求购单时，还会把「新挂 / 成交了几件 / 改价 / 消失」记进 `order_event`，回测里的成交描述用的就是它。
消失的单去哪了（成交 / 被暂停 / 撤单），由下面的「求购成交」查清后写进同一行。

## 选品（价位三期）

看板「选品」页（`/pick`）：自己圈一个池子，看看还有哪些饰品值得挂求购。设计见[价位 spec §9b](superpowers/specs/2026-09-27-price-position.md)。

- **圈池子**：大类、磨损、版本（普通 / StatTrak™ / 纪念品）、具体武器、在售价区间。默认不圈印花、挂件、武器箱 / 胶囊、布章、涂鸦。
  按名字圈出来的最多 500 个：SteamDT 的批量价格接口每分钟只能调 1 次、每次 100 个，价格区间要等取完价格才筛得了。
- **跑一次**：取价格（每批 100 个，批间 65 秒）→ 按价格区间筛 → 取日线（写进自有日线表）→ 估值、给结论。500 个约 13 分钟。
  23:40～00:50 是价格快照和估值的时间，这段时间不开始，正在跑的会暂停。**只请求 SteamDT，不碰悠悠。**
- **结论**：可以挂（上限够得着悠悠最高求购的 90%，给建议出价）/ 观望 / 不建议（上限 ≤ 0 或难出手）/ 不评价（日线不足、没有在售价）。
  **刚从低点涨上来的判观望**：现价比近 60 天最低收盘高 30% 以上（`rebound_window` / `rebound_max`，[回测](research/2026-11-23-pick-rebound-backtest.md)：这类之后 14 天吃亏的概率明显更高）。
  表格「一年里的位置」下面写「近 60 天低点 +N%」，一年高低差 3 倍以上的再写「炒过」（只作说明）。
  悠悠最高求购用 SteamDT 给的，是所有子队列（含条件单）里最高的，偏保守；刀、手套的这个价常常比在售价还高。
- 每次运行的条件和结果存库，保留最近 10 次。

## 市价提醒

两种情况推一条微信（满足任一就推），总览「离第 1」列下面加标签。设计见[市价提醒 spec](superpowers/specs/2026-10-15-market-alerts.md)。

- **榜首高于在售**：求购第 1 名 ≥ 悠悠在售最低，而我排前 3 名；或者排第 4～10 名、我的价 ≥ 在售最低的 85%（`[market_alerts] rank_always` / `rank_max` / `inverted_ratio`；85% 是 16 笔真实成交的下四分位）。卖家直接卖给高价求购比挂出去赚得多，前面的单会被很快吃掉，可能很快轮到你。
- **贴近市价**：我的价 ≥ 在售最低 × 0.9（`near_ratio`），一成交差价就很薄。

推送前用公开接口核对一次实时在售价（每轮最多 `verify_max` 张，计入每小时请求上限）；第 2～10 名里在售价超过 30 分钟没查过的单也会被探一下。
同一张单同一段只推一次：改价后按新价重判，两种情况都不成立才算这一段结束。只看不限条件的单，交易中的不推。

## 求购成交、交易中

「升到第 1 名」只是成交的前兆，5 分钟一轮抓不住集中抛售，Mac 睡着时更是一条都抓不到。所以另外推两类
（[成交推送 spec](superpowers/specs/2026-10-02-fill-alerts.md)、[ADR-0015](decisions/0015-push-fills-and-in-trade.md)）：

- **交易中**：悠悠给的名次是 `*`，说明有卖家卖给了这张单、交易还没完成（实测比成交早 15～27 分钟）。下一轮就推。
- **求购成交**：单子从「求购中」消失后，用同一个「我的求购」接口换 status，到「已完成」（40）、「暂停中」（30）里
  按单号查去向（只读）。成交了、而且之前没推过「交易中」才推，正文带成交时间；Mac 睡着期间成交的，醒来后
  24 小时内补推，并注明晚了多久。**一次成交只推最早的一条。**
- 被悠悠暂停（求购余额不够时会自动暂停）、撤单都不推。推送失败下一轮重试。

总览「全部求购」上方有「最近成交」卡片（近 30 天件数、金额、每天的小柱图、每笔是靠哪条推送知道的），
表格里交易中的单显示「交易中」胶囊、排在第 1 名之前。

    uv run python -m skinpulse fills backfill     # 给以前消失的单补查去向（真请求悠悠，只读；只写去向，绝不推送）

`[fills]`：`max_pages`（每轮每个列表最多翻几页，每页 40 条）、`resolve_window_h`（消失后多久内继续查）、
`notify_window_h`（成交后多久内还推送）。

## 盈亏

看板「盈亏」页：一共赚了 / 亏了多少，其中已经落袋的（已实现）和还拿在手里的（浮动）各多少，按月、按品类、
按单品拆开（[盈亏 spec](superpowers/specs/2026-11-24-pnl.md)、[ADR-0024](decisions/0024-pnl-ledger-fifo-per-platform.md)）。
对悠悠只读：只用「我的买入 / 卖出订单」「库存」「租出中」几个查询接口。

第一次用先导入全部历史（每个启用的悠悠号的买入、卖出都翻到底，每张卖出查一次实际到手价，几分钟）：

    uv run python -m skinpulse pnl import     # 真请求悠悠（只读）；可以重复跑，已入库的订单不会重复
    uv run python -m skinpulse pnl show       # 只读库，打印最近一次的摘要；--basis net 按到手价，--account 2 只看某个号
    uv run python -m skinpulse pnl run        # 手动跑一次每日任务

导入时持仓里还没有价格的饰品会现查一次 SteamDT 批量价；暂停单检查或选品正在跑时不查（它们正占着 `/price/batch` 一分钟一次的配额），
等当晚 23:50 的价格快照补上。

之后每天 `[pnl] run_at`（默认 00:45）自动同步当天新的买卖、拉一次库存和租出，记一份持仓快照（算的是前一天），
平时 10 个请求以内。23:50 的价格快照顺带给持仓里的饰品存价格。

口径（用户 2026-11-24 定）：

- **先进先出，跨平台**：悠悠和 BUFF 的买卖都算（接了 BUFF 号的话）。一笔卖出先配同号同平台最早买进来的那批，不够再配
  别的号、别的平台更早买的同一饰品（按英文名认），所以悠悠买、BUFF 卖也能配上。卖出之前找不到可配的买入（历史开始之前
  买的、别处来的），这笔卖出记「成本未知」，不算盈亏，单独列出。
- **已实现** = 卖出到手价（平台给的，已扣手续费：悠悠 1%，BUFF 1.5%～5% 不等）− 配到的成本。**提现费不扣**。
- **浮动**：持仓按 SteamDT 给的悠悠在售最低价（23:50 快照）估值。页面上能切「按市价」/「按到手价」（扣让价 1%、手续费 1%），
  默认按市价（`[pnl] basis`）。没有市价的饰品成本也不算进浮动。在售很少（< 3 件）或悠悠、BUFF 价差超过 1.5 倍的，
  市值旁边有个小圆点提示价格可能不稳，但照样算。
- **在哪**：持仓逐件对上库存（悠悠、BUFF 看到的是同一个 Steam 库存，同一件只算一次）和悠悠租出，剩下的是「不在库存」：
  账上还在，库存和租出里都没有，也没在悠悠或 BUFF 卖掉，多半是在 BUFF App 里租出去了（网页拿不到出租列表）。
  不在库存的照样算进持仓。
- **不算**：租金（拿不到到账历史）、提现费；库存里没有买入记录的饰品（掉落、别处买的）不进持仓，页脚一行带过。
- 页面上的对照数是悠悠自己算的浮动盈亏（只算它记得买入价的那些件），两者差得多说明哪边记漏了。

`[pnl]`：`run_at`、`basis`、`max_pages`（每天每个列表最多翻几页）、`detail_per_run`（每天最多补几张卖出到手价）、
`thin_count`、`spread_ratio`（价格提示的门槛）。
## 充值前检查暂停单

求购余额不够时，悠悠会把单子自动移进「暂停中」；一充值，这些单子自动回到「求购中」。暂停期间行情在变，恢复那一刻
可能直接排第 1，甚至高于在售最低价（倒挂），几分钟内就会被卖家吃掉。所以**充值前先查一次**，把危险的单在悠悠里
改价或撤掉。设计见[暂停单 spec](superpowers/specs/2026-11-24-paused-order-check.md)。只读、不推送。

- **看板**：总览最上面的「暂停中的求购单」卡片，点「检查一次」。服务在后台跑，约 8 分钟，可以离开页面。查完卡片上是
  四档的张数和占用金额（倒挂 / 直接第 1 / 离第 1 差 5% 内 / 贴近在售），点一档看明细，每行有跳到悠悠商品页的按钮。
  结果超过 2 小时、或者检查之后又有单被暂停，卡片会提醒再查一次。
- **命令**（服务在跑时优先用看板：看板的检查和每轮监控错开，命令不错开）：

      uv run python -m skinpulse check-paused                 # 全部启用的号，结束打印分档表
      uv run python -m skinpulse check-paused --account 2     # 只查一个号
      uv run python -m skinpulse check-paused --json          # 和 /api/paused 一样的 JSON

一次检查做三件事：翻所有号的「暂停中」（每页 40 张，500 张约 13 页）；用 SteamDT 批量价查在售最低（每批 100 个、
1 次/分钟，约 6 分钟）；最贴近在售价的最多 30 张再用悠悠在售接口实时核对。**不逐个查公开求购队列**：2026-11-24 连查
77 次就被悠悠回了 403，正式服务的抽样也跟着失败了将近一小时。第 1 名的价用暂停单列表里悠悠给的子队列榜首价
（和实时榜首基本一致，偶尔差 1 元），所以只知道「是不是第 1、差多少」，不给具体排第几。

暂停单列表里的时间是**被暂停的时刻**，卡片上每张单都写「暂停 N 天」，超过 60 天的醒目标出来（服务上线前暂停的老单，
价格往往早就和市场脱节）。同价时恢复后排前排后没验证过，写「并列第 1」。

`[paused_check]`：`near_gap`（差多少算「差 5% 内」）、`sell_ratio`（贴近在售的比例）、`verify_max`、`old_days`、
`max_pages`（每个号最多翻几页）、`stale_h`（结果多久算过期）。

## 多平台对账（SteamDT）

悠悠的价格相对同类平台是偏高还是偏低？这件事直接影响看板上那个「市场价」能不能当基准用。
数据源是 [SteamDT 开放平台](https://open.steamdt.com)，需要自己申请一个免费 API key。

```bash
uv run python -m skinpulse steamdt-key            # 保存 key（进系统钥匙串，不进仓库）
uv run python -m skinpulse steamdt-items          # 同步饰品目录，建立 templateId ↔ marketHashName 映射
uv run python -m skinpulse market-check           # 对账
```

### 配额是这个接口最硬的约束

| 接口 | 配额 | 用途 |
|---|---|---|
| `/price/batch` | **1 次/分钟**（一次最多 100 个名字） | 批量对账唯一划算的接口 |
| `/price/single` | 60 次/分钟 | 单件查询 |
| `/base` | **1 次/天**（约 11 MB / 4.4 万条） | 饰品目录，必须落盘缓存 |

`/base` 用掉当天那一次就没有第二次了，所以 `steamdt-items` 支持 `--from-file` 从落盘的响应重建
映射；不带 `--from-file` 时会先要你确认。`market-check` 自己在批之间等 65 秒，425 个模板大约跑
4~5 分钟。

**超过 100 个名字的批量请求，服务端只回一句 `100002 参数错误`**，不说是哪个参数、也不说上限
多少，而且照样算掉一次配额。客户端在发出去之前就拦住了。

### 映射走 ID，不走名字

`/base` 的 `platformList` 里带着每个平台的 itemId，而 **YOUPIN 的 itemId 就是悠悠的 templateId**
（实测核对过）。所以映射是精确的，不需要匹配中文名——名字匹配有多不靠谱，实测当场就有例子：
「人工染色」的英文是 `Stained` 而不是 `Case Hardened`（后者是「表面淬火」）。

### 参照平台怎么选

| | 参照 | 为什么 |
|---|---|---|
| 卖方（在售价） | BUFF / C5 / HALOSKINS | 实测这三家在我们的饰品上全覆盖 |
| 买方（求购价） | BUFF / C5 | **只有这两家有求购数据**，HALOSKINS 一件都没有 |

**Steam 故意不算进参照**：它收 15% 手续费、结算在 Steam 钱包里出不来，和国内这几家不是同一个
市场。把它纳进来只会系统性抬高参照、把「悠悠偏低」这个结论夸大——一件 AK-47 上 Steam 价
1910、V5ITEM 2111，而国内几家都在 1400 上下，混在一起算「全平台均价」得到 1618，看着像悠悠低了
13.7%，实际它比国内同行只低 1.6%。

### 详情页与大盘页

两条硬约束，改页面时别破坏：

- **页面绝不直接请求悠悠。** 悠悠的数据全部从数据库读（由监控服务写入）。悠悠通道有风控，监控为此排了
  节奏、配了每小时上限，看板刷新一下就多打一次悠悠，等于绕过了这些保护。
- **外部行情一律走缓存。** 大盘两个接口不在 SteamDT 的配额表里，实测几分钟 3 次就回 `4005`「当前接口
  请求已达到上限」。缓存时长：各平台价格 5 分钟、单品日线 1 小时、大盘最新 10 分钟、大盘日线 6 小时。
  撞上配额时**有旧数据就显示旧数据并标明「刷新失败」和获取时间**，没有才显示错误。撞上 4005 以后，同一份数据
  5 分钟内不再重试（限流期间再请求只会继续 4005）。

图表由前端的 ECharts 画（按需引入，只进详情、分析、大盘三页的包，首页不加载），**涨红跌绿**。
这几页打开时各请求一次接口，切换范围和缩放都在前端做，不会再去请求 SteamDT。几处实测得来、不看代码
很容易弄错的细节：

- SteamDT 的 K 线数组是 **`[时间, 开, 收, 高, 低]`**，不是 OHLC。解析时拿「高 ≥ 开/收 ≥ 低」守着，
  顺序一旦变了会直接报错，而不是画出一张看着像真的错图。接口原样按这个顺序返回，转成 ECharts 要的
  `[开, 收, 低, 高]` 只在 `frontend/src/charts/kline.ts` 一处做（有 vitest 守着）。
- K 线 `type` 1/2/3 是**小时（约 90 天）/ 日（365 天）/ 周（单品从 2022-07 起、大盘从 2023-07 起，中间可能缺几段）**，文档没写。
- 大盘的 `diffYesterdayRatio` **已经是百分数**（0.4482 表示 0.448%），不要再乘 100。
- 流动性差的饰品会有离谱的影线（实测一件 600~1000 的刀，有两天最高价记成了 11178）。纵轴按**实体**
  定范围（后端 `analysis/kline.py`，1 月 / 3 月 / 1 年各算一份），离谱的影线截断画到边上，并**在图上写明
  截断了几根、极值多少**——不悄悄藏掉。
- K 线不含成交量，所以没有「量比」这个信号。
