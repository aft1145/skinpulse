## 0. 一句话

目的是赚差价，所以要回答的问题是：**按这个价买进来，扣完手续费、提现费、让价，再扛过 7 天交易保护期，还能剩多少**。

做法分三步：
1. 每天夜里给所有活跃求购单的饰品存一份悠悠日线；
2. 算出描述标签和扣费差价；
3. 在总览的「价位」视图和详情页的「当前价位」卡片里展示。

一期只描述；二期回测后打开建议（§9）；选品在三期（§9b，2026-10-09 补全）。

## 1. 范围

**一期做：**
- 自有日线：`daily_bar` 存单品日线，`index_daily` 存大盘日线。
- 成交事件：`order_event` 表。
- 纯逻辑模块 `analysis/valuation.py`。
- 每日估值：新定时任务，加上启动补跑；结果写进 `valuation` 表。
- `/api/overview`、`/api/item/{id}` 新增字段。
- 总览加「排名 / 价位」切换和价位视图；详情页加「当前价位」卡片。
- 配置 `[valuation]`。

**一期不做：**
- 建议：可以加价 / 保持 / 考虑降价 / 考虑撤单 / 不评价。视觉稿里的「二期」开关只是预览，二期回测后再做（§9）。
- 选品池、品类解析、全目录搜索（三期）。
- 推送。估值结果不进告警，也不进简报。
- 在系统页的参数设置里改 `[valuation]`。一期只能改 `settings.toml`，看板可以只读展示。
- 对悠悠发任何新请求。估值只用库里已有的数据和 SteamDT。

## 2. 视觉稿阶段的实测（2026-09-27，作者账号里的全部在途求购）

这些数字决定了下面的几处取舍。算法和本 spec 一致。数据来源：
- 当天取到的悠悠日线；
- 09-26 的价格快照。

| 发现 | 数字 | 影响 |
|---|---|---|
| 纸面差价很大 | 按我的价成交，扣费净差价中位数 124% | 「目标差价」这道线只是托底 |
| 抢第 1 往往不划算 | 抢到第 1（榜首 + 0.01）后：约 19% 仍有 ≥ 15%，约 20% 会亏；中位数 3.6% | 「抢到第 1」列是价位视图的主列，标题也用它 |
| 一年低位几乎人人都是 | 68% 处在一年低位，约 71% 在跌；大盘 30 天 −5%、90 天 −17%、1 年 −49% | 分位必须和「相对大盘」「趋势」一起看，不能单独当结论 |
| 规则建议偏激进 | 「在跌且跑输大盘」约占 36%。按 intent 里的草拟规则，几乎全部都会被判「考虑撤单」 | 正说明建议要先回测，一期不上 |
| `ALL` 和 `YOUPIN` 两种 K 线几乎一样 | 20 件对比：收盘价比值、一年分位差的中位数都是 0，分位最大差 12 个点 | 只取 `YOUPIN`，省一半请求 |
| 取数耗时 | 432 次 K 线请求约 12 分钟（每次约 1.7 秒，含间隔） | 夜间任务来得及 |

## 3. 数据

### 3.1 新表（迁移 0008）

**`daily_bar`**：自有单品日线。
- 字段：`template_id`、`platform`（一期只有 `YOUPIN`）、`date`（本地日期，`settings.timezone`）、`open`、`close`、`high`、`low`（Numeric，与 `price_daily` 同精度）、`fetched_at`（UTC）。
- 唯一键：(`template_id`, `platform`, `date`)。
- 写入规则：
  - **只存已收盘的日子**。本地日期 ≥ 运行当天的那根（SteamDT 日线的最后一根还没收盘）不存。
  - **已有的行不覆盖，最近 3 天除外**。原因：SteamDT 的历史会变，周线 4 天里就多出过两段缺口；而当天前后几根可能被 SteamDT 修正。
  - 价格为 0 或解析不了的那根，整根不存（0 = 没有数据）。

**`index_daily`**：自有大盘日线。
- 字段：`date`、`open`、`close`、`high`、`low`、`fetched_at`。
- 唯一键：`date`。写入规则同上。

**`valuation`**：每天每个模板的估值结果。
- 字段：`date`（估值覆盖的本地日期 D）、`template_id`、`computed_at`（UTC），以及 §4 的全部字段：
  - 标签用字符串；
  - 数字用 Numeric；缺失为 NULL，**不填 0**。
- 唯一键：(`date`, `template_id`)。
- 页面读的是每个模板最新一天的那行。

**`order_event`**：求购单的变化，给二期回测校准成交用。
- 字段：`id`、`purchase_no`、`template_id`、`kind`、`qty_before`、`qty_after`、`price`、`at`（UTC）。
- `kind` 的取值和记录时机，都在同步（`services.account.sync_my_orders`）时判断：

  | kind | 什么时候记 | 说明 |
  |---|---|---|
  | `filled` | `remaining_qty` 比上次少了，扣掉改件数造成的那部分还有剩 | 确定成交了 `qty_before − qty_after` 件 |
  | `gone` | 单从列表里消失 | 成交、撤单、到期都有可能，悠悠的列表接口**分不出来**。二期校准时只把它当「可能成交」 |
  | `new` | 第一次同步到这张单 | |
  | `repriced` | 价格变了 | 用户在悠悠里改了价 |
  | `resized` | 总件数 `qty` 变了 | 用户在悠悠里改了件数；`qty_before` / `qty_after` 是总件数。改件数不算成交 |

- 同步本身的行为不变。记事件失败只记 WARNING（异常类型名），不能影响同步和监控。

### 3.2 外部请求

- **单品日线**：SteamDT `item/v1/kline`，`type=2`（日），`platform=YOUPIN`。
  - 每个活跃模板一次，按 `valuation.rate_per_min`（默认 60，是配额 120 次/分钟的一半，另一半留给看板）限速。
  - 没映射的模板跳过并计数。
- **大盘日线**：走 `MarketData.broad_kline` 的缓存（和大盘页共用，6 小时），**不单独请求**。大盘接口很容易 4005。
- **在售价、在售数、最高求购**：读当天 23:50 的 `price_daily`（悠悠、BUFF 两行），不另外请求。
- **我的价、榜首价、名次**：用总览那一行里的值（我的价来自 `my_buy_order`，榜首价和名次来自最新的排名快照，和页面上的排名显示同一个来源），不请求悠悠。

## 4. 计算（`analysis/valuation.py`，纯逻辑、无 IO）

输入：
- 一个模板的日线（已收盘，按时间升序）；
- 同期大盘日线；
- 悠悠、BUFF 的 `price_daily` 行；
- 这个模板上我的单：价格、子队列榜首价、名次、是否条件单；
- 配置。

输出一个 `Valuation`。**所有阈值都是模块里有名有姓的常量，附注释说明来历**，和 `signals.py` 的做法一样。

### 4.1 价位与走势

| 字段 | 算法 | 标签 |
|---|---|---|
| `bars` | 用到的日线根数（最近 365 根） | 少于 `min_bars`（60）根：本节全部为 NULL，数据标签写「数据不足」 |
| `pct` | 最近 365 根收盘价里，≤ 最新收盘的占比 | ≤ 0.20 一年低位；≥ 0.80 一年高位；其余中位 |
| `lo`、`hi`、`cur` | 一年收盘价的最低、最高、最新 | |
| `trend` | 复用 `signals.compute`，MA7/MA30 偏离 ±2% | 上升 / 横盘 / 下降 |
| `c30`、`c90` | 最新收盘相对 30 根、90 根之前的涨跌 | |
| `b30`、`b90` | 大盘同期涨跌（按日期对齐，不按根数） | |
| `ex30` | `c30 − b30`（百分点） | > +3 跑赢大盘；< −3 跑输大盘；其余持平 |
| `vol7` | 日对数收益的 EWMA 标准差（λ = 0.94，前 20 根做初值）× √7 | < 5% 波动小；> 12% 波动大；其余波动中 |
| `q10` | 一年里所有 7 天涨跌（`c[t+7]/c[t] − 1`，窗口重叠）的第 10 百分位，最近秩次法不插值 | 显示为「7 天坏情况」 |

「按日期对齐」的意思：大盘和单品都取同一个本地日期的收盘价。缺那天就往前找最近的一天；往前 3 天内都没有，就算 NULL。

### 4.2 出手难易

- `listed` = 悠悠在售数 + BUFF 在售数。
- `spread` =（悠悠在售最低 − 悠悠最高求购）/ 悠悠在售最低。
- 标签：
  - 好出手：`listed ≥ 100` 且 `spread ≤ 5%`；
  - 难出手：`listed < 20` 或 `spread > 20%`；
  - 其余一般。
- 没有悠悠在售价时为 NULL。

### 4.3 扣费差价

- 每个平台的到手价 = 在售最低 × (1 − 让价) × (1 − 该平台交易手续费) × (1 − 提现费)。
  - 默认：让价 1%，悠悠 1%、BUFF 1.5%，提现 1%。
  - 只算有在售价的平台。
- `exit`、`exit_where`：两个平台里到手多的那个，以及是哪个平台。
- `m_my` = `exit / 我的价 − 1`。
- `m_top` = `exit / (榜首价 + 0.01) − 1`，即抢到第 1 的差价。
  - 我已经是第 1 时为 NULL，页面写「已是第 1」。
  - 没有榜首价时也为 NULL。
- `m_bad` = `exit × (1 + q10) / 我的价 − 1`，即按我的价成交后，7 天里碰上坏情况的差价。
- `cap`（二期建议要用，一期只存不显示）= `min(exit × (1+q10) / (1 + 目标差价), exit × (1+q10) − 最低利润)`。
- 同一个模板挂了多张单时，按每张单各算 `m_my`、`m_top`、`m_bad`。**这三项在接口里算，不存进 `valuation` 表**：表里只存与单无关的部分，这样改价后不用等第二天。

### 4.4 条件单

带磨损区间、款式条件的单，照样给数字。页面标注「K 线按整个磨损档算」；二期对它们不给建议。

## 5. 任务（`scheduler.py`）

| 任务 | 时间 | 做什么 |
|---|---|---|
| `valuation` | 每天 `valuation.run_at`（默认 00:30，`settings.timezone`） | 针对刚结束的本地日 D：<br>1. 取活跃模板的日线，写进 `daily_bar`；<br>2. 取大盘日线（走缓存），写进 `index_daily`；<br>3. 读 D 的 `price_daily`，逐个模板计算，写进 `valuation(D, …)` |
| 启动补跑 | 服务启动时一次 | 最近一个已到点的 `run_at` 对应的 D **没算全**（有映射的活跃模板没有每个都有一行，比如 00:30 那次算到一半断了），而且没超过 12 小时，就补跑（和简报的补发同一个思路） |

- `max_instances=1`，`coalesce`，`misfire_grace_time` 12 小时。
- 失败只记日志（异常类型名），**不影响监控和告警**。
- 单个模板失败只跳过这个模板，计数写进日志；配额错误（4005）等 65 秒重试一次，再失败就跳过。
- 同一天重跑是安全的：`daily_bar` 按规则写；`valuation` 同一天的行整行覆盖，因为估值结果可以重算。
- D 没有 `price_daily`（23:50 快照没跑），照样算价位和走势；扣费差价、出手难易为 NULL，页面写「没有价格快照」。
- 手动命令 `valuation [--date YYYY-MM-DD] [--dry-run]`：dry-run 只打印汇总、不写库。**任务真的会请求 SteamDT**。

## 6. 接口

### 6.1 `GET /api/overview` 新增

- 顶层加 `valuation`：
  - `as_of`：估值覆盖的日期；
  - `computed_at`；
  - `snapshot_date`：用的是哪天的价格快照；
  - `counts`：`take`（`m_top ≥ 目标差价`）、`take_loss`（`m_top < 0`）、`low`、`fall`（下降且跑输大盘）、`hard`（难出手）、`evaluated`、`insufficient`；
  - `fees`：给页面那句「差价已扣……」用。

  从来没算过估值时整个为 null。
- `orders[]` 的每张单加 `value`：
  - 字段：`as_of`、`pct`、`pct_label`、`trend`、`rel`、`c30`、`c90`、`b30`、`b90`、`ex30`、`q10`、`liq`、`listed`、`spread`、`vol7`、`vol_label`、`bars`、`lo`、`hi`、`cur`、`exit`、`exit_where`（`YOUPIN` / `BUFF`）、`exit_sell`、`m_my`、`m_top`、`m_bad`、`conditional`；
  - 详情页 `/api/item` 的 `orders[]` 也带同样的 `value`（和总览的行一字不差）；
  - 没估值时为 null。
- 性能：一次查询取出每个模板最新一天的 `valuation`，不逐单查询。`/api/overview` 的耗时目标不变（见看板 spec §9 的已知偏离）。

### 6.2 `GET /api/item/{id}` 新增

- `valuation`：
  - 上面的全部字段，外加 `c90`、`b90`、`ex30`；
  - `series90`：近 90 天单品和大盘的收盘，`[[date, item, broad]]`，从自有表读，缺失为 null；
  - `computed_at`、`snapshot_date`，以及和总览同一份的 `fees`、`target_margin`（扣费明细的文字要用）。
- 按 `template_rows` 里排名最好的那张单算 `m_my`、`m_top`、`m_bad`，和「我的求购」卡片默认显示的那张一致；卡片切换单时，前端用同一份 `exit` 重算这三项。

## 7. 页面

### 7.1 总览：「排名 / 价位」切换

- 标题行右边加一个两段切换，排名是默认。切换写进 URL（`?view=value`），刷新后保持。
- 价位视图的布局按视觉稿：
  - **标题**：「**N 张**抢到第 1 仍有 15% 差价」。副标题：「其余 M 张抢到第 1 后差价不到 15%，其中 K 张会亏 · 按 MM-DD 价格快照」。15% 取配置里的目标差价。
  - **三张提示卡**：处在一年低位、在跌且跑输大盘、难出手。点一下按这一项筛选，再点一下取消；筛选状态显示在表头，可以清除。
  - **表格列**：
    - 饰品；
    - 一年里的位置：小条加分位加标签；
    - 走势：趋势标签、相对大盘标签，下面一行是 30 日它和大盘的涨跌；
    - 7 天坏情况：下面一行写出手难易；
    - 按我的价成交：下面一行写我的价；
    - 抢到第 1：下面一行写「第 N 名 → 出价 X」。
  - **默认排序**：按「抢到第 1」从高到低，NULL 排最后。
  - **展开行**：
    - 一年收盘区间，标出一年低、现价、一年高；
    - 卖出去能拿到多少：在售最低 → 扣掉让价、手续费、提现 → 到手 → 按我的价 / 抢到第 1 / 7 天坏情况；
    - 日线根数、7 天波动、在售数、「查看饰品详情」。
  - **页脚固定一行**：按什么数据、按固定规则算的参考；政策风险算不进去；「—」表示数据不足，不是 0。
- 颜色：
  - 差价为负（会亏）用 `loss`，不用涨跌色，因为涨红跌绿的红表示涨；
  - 趋势标签沿用涨红跌绿；
  - 「跑输大盘」「难出手」用 `warn`；
  - 「抢到第 1 ≥ 目标差价」用 accent。
- 从来没算过估值时，价位视图只显示一行：「还没有估值：每天 00:30 计算，或运行 `valuation`」。

### 7.2 详情页：「当前价位」卡片

- 位置：价格走势网格之后、各平台比价之前，占满整行。
- **标题行**：「当前价位」、标签组（位置、趋势、相对大盘、波动、出手难易），右边写「悠悠日线 N 根 · MM-DD 价格快照」。
- **三栏**，各有一个大数字（用户 2026-09-27 定稿时保留了三个）：
  1. 一年里的位置：分位；一年低、现价、一年高三个点（现价标在条上方，一年低 / 高在条下方）；一句「离一年高点 / 低点多少」。不画「低位区」浅色段：分位按收盘价排序，价格区间的前 20% 和它对不上。
  2. 和大盘比（近 90 天，起点都记作 100）：30 日相对大盘的百分点；两条线，单品实线、大盘虚线；一句说明。
  3. 卖出去能拿到多少：抢到第 1 的扣费差价；下面是逐步扣费和三种差价。
- **页脚**：规则说明，以及「7 天坏情况」的定义。
- 条件单：卡片标题后加一个标签「条件单：K 线按整个磨损档算」。
- 还没有估值时（从没算过、或服务刚启动还在补算），同一位置显示一张只有标题和一句说明的卡片，不整块消失。
- 标题 2026-09-28 按用户要求从「现在的价位」改为「当前价位」。
- 「我的求购」卡片里那句「升上去会推送」按看板的措辞约定去掉（视觉稿已改）。

## 8. 配置 `[valuation]`

```toml
[valuation]
enabled = true
run_at = "00:30"            # settings.timezone
rate_per_min = 60           # 单品 K 线请求限速，配额是 120 次/分钟
min_bars = 60
undercut = 0.01             # 挂卖让价
withdraw_fee = 0.01         # 提现费（BUFF、悠悠都是 1%；悠悠每次最低 2 元，按每次提现收，摊到每件上忽略）
target_margin = 0.15
min_profit = 1.0            # 元
bad_quantile = 0.10

[valuation.fees]            # 卖出成交的交易手续费，用户 2026-09-27 给的实测
YOUPIN = 0.01
BUFF = 0.015                # 2026-04-14 起统一 1.5%
```

- 全部带校验：费率在 0～0.2 之间，`run_at` 用 HH:MM 格式。
- 系统页只读展示，一期不开放网页修改。

## 9. 二期：回测，然后上线建议（2026-10-09 完成，plan（未公开））

2026-10-09 补全。**先回测、按事先写死的标准判通过与否，通过的规则才上线**（ADR-0014）。

### 9.1 有什么数据，缺什么

| 数据 | 有多少 | 能检验什么 |
|---|---|---|
| `daily_bar`（悠悠日线） | 645 个模板，2025-09-29 至今，约 23.6 万根 | 标签和「7 天坏情况」对**之后价格**的预测力 |
| `index_daily`（大盘日线） | 同期 375 天 | 「相对大盘」 |
| `order_event` + 成交去向 | 消失 594 条，其中确认成交 16 条（09-29 起） | 只够描述：成交时排第几名。**不够校准成交模型** |
| `price_daily`（在售价、在售数） | 09-22 起 | 太短，「出手难易」**不能回测**，不进建议规则 |
| 历史求购价、榜首价 | 只有现在的 | 「按我的价」的差价**不能回测**，只能借「坏情况」准不准来间接检验 |

先天局限（写进研究报告开头）：
- 只有一年，而且这一年大盘跌了约一半，只覆盖了一种行情；
- 模板都是用户挂过单的（选择偏差）；
- 日线收盘价当作卖出价，实际卖出要比这晚、还有让价。

### 9.2 回测方法（walk-forward）

- 对每个模板、每个日子 t（从第 `min_bars` 根起，每 5 天取一个样本，避免样本高度重叠）：只用 ≤ t 的日线和大盘，调用**同一个** `analysis.valuation.compute` 算出当天的标签和 `q10`。不另写一套算法，保证回测的和页面上的是同一个东西。
- 结果变量：`r7 = c[t+7]/c[t] − 1`（7 天交易保护期），`r14 = c[t+14]/c[t] − 1`（保护期加上挂出去卖的时间）。没有 t+14 的样本不要。
- **两段**：H1 = 2026-04-01 之前，H2 = 2026-04-01 及之后。H1 用来选参数，H2 只用来验证；一条规则要两段都过。
- 按大类（`analysis.category`）、按月拆开报。
- 纯 Python，复用现有模块，**不引入 pandas**（ADR-0014 原写「用 pandas」；2026-10-09 探查时纯 Python 跑全部样本只要几秒，不值得加一个依赖。ADR 同步加注）。

### 9.3 要检验的两件事和通过标准（正式跑之前定死）

**R1：「7 天坏情况」准不准。** 建议里的「撤单」「降价」「加价」都靠它：求购价上限 `cap` 是按坏情况倒推的。
- 指标：覆盖率 = `r7 < q10` 的样本占比。设计上应该约等于分位数（第 10 百分位 → 10%）。
- 通过：H1、H2 各自 ≤ 13%；样本数 ≥ 1000 的大类里，每一类 ≤ 15%。低于 10% 只是偏保守，不算失败。
- 不通过时：在 H1 上找能满足标准的最小分位（第 5、7.5 百分位……），拿到 H2 上验证；过了就把 `bad_quantile` 默认值改成它。还不过，就**不上任何靠 cap 的建议**。

**R2：「在跌且跑输大盘」能不能单独作为撤单理由。**
- 指标：被标出的样本对比全部样本：`r14` 中位数、`P(r14 < −5%)`。
- 通过：H1、H2 **都**满足「标出的 `r14` 中位数更低，而且 `P(r14 < −5%)` 高出至少 5 个百分点」。
- 不通过：这条从撤单理由里删掉，只留作描述标签。

**成交描述（不设标准）**：16 条确认成交在消失前最后一次排第几名、价格比当时的收盘价低多少。只用来说明「可以加价」的依据有多弱，样本到 50 条以上再重看。

**探查时已经看到的**（2026-10-09，粗略版本，不能当正式结果）：R1 全部样本 8.6%，H1 5.5%、H2 10.8%，但 2026-05 单月 23%、一年高位的样本 20%；R2 在 H1 里标出的反而更好（中位数 +0.5% 对 −0.1%），在 H2 里差一些。也就是说 R2 很可能不过，R1 可能要改分位或者把「一年高位」单独处理。**标准是在看到这些之前就按 ADR-0014 的思路定的，这里不为了让规则通过而放宽**；如实写进研究报告。

### 9.4 研究报告

- 命令 `backtest [--out PATH] [--split YYYY-MM-DD]`：只读库，不请求任何外部接口，输出 Markdown 表格（全部 / 分段 / 分类 / 分月）。
- 结论写进 `docs/research/2026-10-xx-valuation-backtest.md`：数据、方法、R1/R2 结果、按哪个分位上线、哪些规则删掉了，以及每季度重跑一次的提醒。

### 9.5 建议规则（`analysis/advice.py`，按顺序判断，命中一条就停）

配置 `[valuation] advice = true`（默认打开）；关掉时接口不给 `advice`。

规则只用到通过了回测的部分。阈值是常量或 `[valuation]` 配置，每条建议都带「触发它的规则」一句话。

回测结果（[研究报告](../../research/2026-10-09-valuation-backtest.md)）：R1 按 0.10 通过，R2 不通过。所以撤单只看 `m_bad`，不带趋势条件。

1. **不评价**：交易中、条件单、数据不足（`q10` 为 NULL）、没有在售价（`exit` 或 `cap` 为 NULL）、没有求购价。
2. **考虑撤单**：`m_bad < 0`，也就是按我的价成交、碰上坏情况会亏（正好 0 不算）。
3. **考虑降价**：我的价 > `cap`：碰上坏情况还赚，但不够目标差价或最低利润。写出「降到 X 以内」；`cap ≤ 0` 时写「按规则怎么买都不够」，不给价。
4. **可以加价**：我不是第 1（没名次但知道榜首价也算）、`榜首价 + 0.01 ≤ cap`。写出「加到 X 可排第 1」和加价后的坏情况差价。成交描述显示 16 条成交里 13 条在第 2～6 名，所以文案不说「排第 1 才会成交」。
5. **保持**：其余。已是第 1 写「已是第 1」；抢第 1 会超过上限时写出要出多少。

R1 不通过时，第 2～4 条都不上，二期只交付研究报告，页面不变。

- `value` 里同时给出 `cap`（一期只存不显示，二期展开行要用）。
- `valuation.counts` 加 `advice`：各建议的张数；建议关掉时为 null。
- 总览价位视图：加「建议」列（标签 + 一行规则），表头可按建议筛选；提示卡不变。详情页「当前价位」卡片加一条建议条。布局按视觉稿里「二期」开关预览的样子，动手前在测试实例上对一遍。

## 9b. 三期：小范围选品（2026-10-10 完成，plan（未公开））

2026-10-09 补全。用户定下的：选品池**按品类 + 价格区间圈**，上限 500 个模板，默认排除印花、挂件、武器箱 / 胶囊、布章、涂鸦（intent 原定；「收藏品」目录里没有，品类解析把它归进「其他」，默认也排除）。

### 9b.1 能用的数据和配额

| 数据 | 从哪来 | 代价 |
|---|---|---|
| 候选名单 | `item` 表（SteamDT 目录，35,023 个有悠悠 ID 的模板），品类用 `analysis.category`，磨损、StatTrak™ / 纪念品从英文名解析 | 不请求 |
| 在售最低、在售数、最高求购（悠悠、BUFF） | SteamDT `/price/batch` | **1 次/分钟、每次 100 个**：500 个要 5 分钟 |
| 一年日线 | SteamDT 单品 K 线 | 120 次/分钟，照 `valuation.rate_per_min`（60）限速：500 个约 9 分钟 |
| 大盘日线 | `index_daily`（自有表） | 不请求 |

- **价格区间只能在取完价格之后筛**：目录里没有价格。所以「按名字圈出来的池子」不能超过 500 个，超了让用户再收窄（加武器、磨损、StatTrak 条件）。
- **对悠悠不发任何请求**：悠悠的最高求购用 SteamDT 给的 `YOUPIN` 那一行 `bidding_price`。
  - 2026-10-09 实测（10-08 价格快照 356 个模板）：83% 有这个价。和我们实时核对的「不限条件」子队列榜首比，相等 27%、SteamDT 更低 13%、**更高 60%**：它是所有子队列（含磨损、款式条件单）里的最高价。
  - 所以拿它当「排第 1 要出的价」是**偏保守**的：上限够得着它，在不限条件的队列里一定排第 1。
  - 没有这个价时，分不清是「没人求购」还是「没数据」，不当作可以挂。
- 取到的日线照估值任务的规则写进 `daily_bar`（§3.1），以后估值、回测都能用。

### 9b.2 选品任务

- 看板上点「开始选品」→ `POST /api/pick/runs`（同源 JSON）→ 服务进程里起一个后台线程，同一时间只跑一个。
- 阶段：圈名单 → 取价格（每批 100 个，批与批之间等够 60 秒）→ 按价格区间筛 → 取日线（限速）→ 逐个估值 → 写结果。每完成一步更新进度。
- **夜间窗口不跑**：23:40～00:50 之间（价格快照 23:50 和估值 00:30 都在用同一份配额）拒绝开始，正在跑的到点暂停、过了窗口继续。
- 4005（配额）照估值任务的做法：等 65 秒重试一次，再失败跳过这个模板，计数。
- 服务重启时正在跑的任务记为「中断」，不自动续跑。
- 每次运行的条件、进度、结果存库，保留最近 10 次；结果页打开时不重算。

### 9b.3 每个结果给什么

> **到手价只算悠悠**（2026-11-23）：`exit` 只在 `[valuation] exit_platforms`（默认 `["YOUPIN"]`）里取，原来是悠悠、BUFF 哪家到手多算哪家。总览价位视图和建议用的是同一个 `exit`，下一次 00:30 估值后跟着变。表格「一年里的位置」下面加两行说明：「近 60 天低点 +71%」（到门槛标 warn 色）、「炒过：一年高低差 N 倍」（≥ 3 倍才写）。

用 `analysis.valuation.compute` 算描述（价位、走势、相对大盘、7 天坏情况、出手难易、到手价、`cap`），再给结论（`analysis/pick.py`，纯逻辑，按顺序判断）：

1. **不评价**：日线不足 60 根、没有在售价（悠悠和 BUFF 都没有）。
2. **不建议**：`cap ≤ 0`（按规则怎么买都不够目标差价或 ¥1 最低利润），或者难出手。
2b. **观望：刚从低点涨上来**（2026-11-23，intent（未公开），[R3 回测](../../research/2026-11-23-pick-rebound-backtest.md)通过）：现价 ÷ 近 `rebound_window`（60）根最低收盘 − 1 ≥ `rebound_max`（30%），写「从近 60 天低点涨了 71%，刚涨上来的先不追」。日线不足 60 根时不判。「炒过」（一年最高 ≥ 最低 × 3）回测两段都不过，只在表格里作描述。
3. **可以挂**：`cap` ≥ 悠悠最高求购 × 0.9，**不要求排第 1**（用户 2026-10-09 定；依据：16 条确认成交里 13 条在第 2～6 名。按排第 1 算，10-09 的 357 个模板里只有 4 个可以挂，按 0.9 算 35 个）。**建议出价** = min(`cap`, 悠悠最高求购 + 0.01)，写出这个价大约排第几（等于最高求购 + 0.01 时是第 1，否则写「在榜首之下」）和按它成交、碰上坏情况的扣费差价。
4. **观望**：其余。上限不到悠悠最高求购 90% 的，写出上限和悠悠最高求购各是多少；SteamDT 没给悠悠最高求购的，写「没有悠悠求购价」，只给上限。

- 只用回测通过的东西（R1）。「在跌且跑输大盘」不进结论（R2 没过）。「难出手」不是预测，是现在的盘口太薄，当作前提条件。
- 已经挂了单的模板照样评，标「已挂单」。
- 结论只是参考：不下单、不改价，对悠悠只读。

### 9b.4 页面 `/pick`「选品」
