# BUFF 求购监控（第二期）

- 日期：2026-11-24
- 来源：intent（未公开）（接受）、[ADR-0022](../../decisions/0022-multi-account-first-then-buff.md)、[BUFF 只读接口调研](../../research/2026-11-24-buff-readonly-api.md) §8（登录后实测）、§9（卖出、库存、出租）；盈亏那边的需求见 [ADR-0025](../../decisions/0025-pnl-cross-platform-matching.md)、[盈亏 spec §9](2026-11-24-pnl.md)
- 状态：定稿（用户 2026-11-24：「按建议定稿」，三条待决见文末）
- 前一期：[悠悠多账号](2026-11-24-multi-account.md)（已上线，`account.platform` 已经留好）

## 0. 一句话

BUFF 号作为一个 `platform=buff` 的账号加进来，每 15 分钟同步一次「我的求购」：BUFF 的单和悠悠的单一起显示在总览里，同样会推「升到第 1 名」「交易中」「求购成交」。**只有悠悠号的人什么都看不出变化**；对 BUFF 只读。

## 1. 范围

**做：**
- BUFF 只读适配器 `adapters/buff/`（§3），凭据是浏览器里复制的 `session` cookie（§2）。
- 每 15 分钟一轮 BUFF 监控，和悠悠的轮次分开（§4）；名次按 ADR-0022 的口径自己数，候选靠 `wait_supply` 自带的最高求购价来筛（§5）。
- 名次进现有告警引擎；交易中、成交用 BUFF 订单配对（§6）。
- 推送、总览、系统页、详情页按 BUFF 号适配（§7、§8）。
- 给盈亏统计导入 BUFF 的买入、卖出订单和库存（§9）。

**不做：**
- 价位建议、选品、简报、市价提醒里的 BUFF 单（ADR-0022，到手价仍只按悠悠算）。
- BUFF 在售价、BUFF 行情页。
- 出租：网页版没有接口（调研 §9.3）。
- 跨号的「前面是我自己的号」只在同一平台里判（BUFF 和悠悠的队列是两回事）。
- 一个 BUFF 号以上的情况能跑，但不专门测；用户只有一个 BUFF 号。

## 2. 账号与凭据

- `account` 一行：`platform=buff`、`label` 默认「BUFF」、`nickname` 取 BUFF 昵称、`platform_uid`（新列，BUFF 的 `U` 开头用户号，查重用）。
- 钥匙串：`buff_cookie:<id>`，存 `session` cookie 的值。`secrets.py` 加 `buff_cookie_key(account_id)`。cookie 和 token 一样：**绝不进日志、异常、HTTP 响应**。
- **怎么拿 cookie**（使用手册写步骤）：在 Chrome 里登录 BUFF，勾「10 天内免登录」→ 开发者工具 → Application → Cookies → `buff.163.com` → 复制 `session` 那一行的值 → 看板系统页「添加账号」选 BUFF 粘贴。`session` 是 HttpOnly，页面脚本读不到，只能手动复制（调研 §8.5）。
- **校验**：`wait_supply?page_size=1`，`code:"OK"` 就算有效，顺便拿用户号、昵称（`user_infos`）。`platform_uid` 和已有的 BUFF 号相同就拒绝（409）。
- **有效期**不明：拿到 `Login Required` 就标失效，推「BUFF 登录已失效」（按号、24 小时重复，同悠悠）。实际能用几天写进 known-issues 的观察项。
- 请求头：`User-Agent`、`Accept-Language` 从 `settings.toml [buff]` 读，不硬编码；带 `Device-Id` cookie（按号持久化到 `account.device_id`，第一次用时随机生成）。不读代理环境变量（ADR-0011）。

## 3. 适配器 `adapters/buff/`

和 `adapters/youpin/` 平级：`client.py`、`errors.py`、`models.py`，只做「HTTP → dataclass + 错误码」。

**只读，靠结构保证**：客户端只有一个私有 `_get(path, params)`，没有发 POST / PUT / DELETE 的方法；测试断言整个 `adapters/buff/` 里没有别的 HTTP 动词。`guard_youpin_writes.py` 加拦 BUFF 的写路径（实现时没改名：改名会让正在跑的会话找不到 hook，见 plan 偏离记录）（`buy_order/create`、`buy_order/cancel`、`sell_order/create`、`goods/buy` 等，具体列表在 plan 里定）。

| 方法 | 接口 | 用途 |
|---|---|---|
| `my_buy_orders()` | `/api/market/buy_order/wait_supply?game=csgo&page_size=60`，翻到空页 | 同步 |
| `buy_queue(goods_id, page)` | `/api/market/goods/buy_order?game=csgo&goods_id=&page_num=&page_size=100` | 数名次 |
| `buy_history(page, size)` | `/api/market/buy_order/history?game=csgo` | 交易中、成交；盈亏买入 |
| `sell_history(page, size)` | `/api/market/sell_order/history?game=csgo` | 盈亏卖出 |
| `inventory(page)` | `/api/market/steam_inventory?game=csgo&force=0&state=all&page_size=500` | 盈亏库存 |

`/account/api/user/info/v2` **不调**（只返回个人资料，调研 §8.4）。库存只用 `force=0`。

**数据类**（`models.py`）：`BuffBuyOrder`（单号、`goods_id`、价格、`num`、`real_num`、`specific`、`buy_max_price`、建单时间、`market_hash_name`、中文名）、`BuffQueueRow`（单号、`user_id`、价格、`num`、`specific`、建单时间）、`BuffBill`（订单号、`goods_id`、`type`、`state`、价格、`fee`、`income`、`created_at`、`transact_time`、`assetid`）、`BuffAsset`。对手的 `user_id`、昵称、Steam ID **不进数据类**（买家、卖家都是），解析时就丢掉。金额一律 `Decimal`。

**错误码**（`errors.py`），HTTP 永远看业务码，外加 BUFF 自己的几种：

| 情况 | 异常 | 处理（§4） |
|---|---|---|
| `code:"Login Required"` | `BuffLoginRequired` | 标失效、推提醒、这个号停到换 cookie |
| HTTP 429 + HTML、`Captcha Validate Required`、正文含「系统繁忙」「请求过于频繁」「人机验证」、HTTP 403 / 412 | `BuffRateLimited` | 暂停这个号 `buff.pause_hours`（默认 2 小时），推一条「BUFF 访问受限，已暂停」，不重试 |
| 其它非 `OK` | `BuffError(code)` | 这一轮跳过这个号，记 warning |
| 传输层异常 | 原样抛 | 只记类型名（URL 里可能带参数） |

## 4. BUFF 轮次

**运行时**：`rt.accounts` 仍然**只放悠悠号**。盈亏、暂停检测、心跳、换 token 都拿它当悠悠客户端用，BUFF 号放进去会被当成悠悠号请求。BUFF 号单独放在 `rt.buff_accounts: dict[int, BuffAccountRuntime]`（`id`、`label`、`client`、`login_notice`），看板添加、停用 BUFF 号时就地改它，不用重启（和多账号一期一样）。

- 新 job `buff_round`，每 `buff.round_interval_min`（默认 15）分钟一次，`max_instances=1`。和悠悠的 `monitor_round` 互不等待；SQLite 已经是 WAL，现在别的任务也并发写。
- 夜间：沿用 `polling` 的夜间时段和倍数（0–8 点间隔翻倍）。
- **请求间隔**：同一个号的两次请求隔 ≥ `buff.request_gap_s`（默认 6，最小 5）秒，加 30% 抖动。
- 一轮的步骤（每个启用的 BUFF 号依次）：
  1. 暂停中就跳过。
  2. `my_buy_orders()` → `sync_buff_orders(session, acc)`：和悠悠的 `sync_my_orders` 同一套语义（新单 `new`、改价 `repriced`、部分成交 `filled`、消失 `gone`，「消失」只在本号判），只是数据来自 BUFF。
  3. 数名次（§5）：最多 `buff.queue_per_round`（默认 10）次队列请求。
  4. `buy_history` 第 1 页（20 条）：找交易中、给消失的单配对成交（§6）。
  5. 写快照、走告警引擎、推送：复用 `Monitor` 现有的 pass A 后半段（写 `RankSnapshot`、`AlertEngine.step`、`NotificationLog`、`_notify`）。实现时把这一段从 `run_round` 里抽成一个方法，两边共用。
- 一轮请求数：1（求购单）+ ≤ 10（队列）+ 1（订单）= 最多 12 次，按 15 分钟一轮约 48 次 / 小时。
- 状态 key：`buff_account:<id>`（`system_status`），系统页、`/api/meta` 按它显示。
- **只有悠悠号时**：不注册 `buff_round`，不发任何 BUFF 请求。

### 单号、饰品、队列

- 单号：`purchase_no = "buff:" + 原单号`（ADR-0022），前缀只在适配器边界加、去。
- 饰品：`goods_id` → 悠悠 `templateId`。先查 `item.buff_goods_id`；没有就查 SteamDT `/base` 缓存的 `platformList` 里 `BUFF` 那一项（调研 §8.6，4/4 对上），再退一步按 `market_hash_name` 找 `item.hash_name`；找到就把 `buff_goods_id` 记进 `item`。**都对不上**：照样监控，`template_id = -goods_id`（负数 = 只在 BUFF 有），这类单没有详情页。
- `queue_key`：`buff:<goods_id>:plain`；条件单是 `buff:<goods_id>:<条件指纹>`（`specific` 按 `type` 排序后的 `type=values` 拼接）。`queue_key_from_str`、`_queue_label` 认出 `buff:` 前缀就走 BUFF 的分支。队列标签：普通单「不限」，条件单用 `specific` 的 `text`（如「磨损: 0.15-0.18」）。

## 5. 名次

口径（ADR-0022）：**普通单只和普通单比，条件单只和条件完全相同的单比**；同价先挂的在前。另外记「前面还有几张条件单」，只显示、不进告警。

**候选**（这一轮要查队列的单，按顺序取，取满 `queue_per_round` 为止）：
1. 普通单且 `price ≥ buy_max_price`：可能是第 1（`buy_max_price` 只算普通单，调研 §8.2）。
2. 告警状态是 ALERTING 的单：要知道它什么时候掉出去。
3. 其余的单按「上次数名次的时间」从早到晚轮换。

用户现在 8 张单，每轮全部查得到；单多了以后前两类优先、其余轮着来。

**不查队列的普通单**：`price < buy_max_price` 已经说明不是第 1，名次记 `None`、榜首记 `buy_max_price`。告警引擎拿到 `None` 不动状态（`AlertEngine.step` 本来就这样），而 ALERTING 的单每轮都在候选里，不会卡在告警中。

**数法**：取队列第 1 页（100 条）；我的单不在这一页、而且这页最后一条的价还不低于我的价，就翻下一页，最多 `buff.queue_max_pages`（默认 3）页；还找不到就名次 `None`、`beyond` 记已看过的条数（看板显示「300 名以后」）。
- 普通单：名次 = 1 + 普通单里（价比我高，或同价、建单比我早）的张数；榜首 = 普通单最高价。
- 条件单：只数 `specific` 和我完全相同的单；榜首是这些单的最高价。
- 条件单挡路：价比我高（同价早）的**其它**单的张数，写进 `my_buy_order.cond_ahead`。
- 数名次时排除**我自己这张**（按单号）。同一个号在同一队列的另一张单照常算。
- 纯函数放 `core/buff_rank.py`，用实测队列的 fixture 测。

**告警**：和悠悠同一个引擎、同一套设置（`enter_rank`、`exit_rank`、`confirm_rounds`、`max_gap_ratio`）。不做悠悠那套「实时核对」：BUFF 的名次本来就是当场数的。

## 6. 交易中、成交

BUFF 的订单**不带求购单号**（调研 §8.4），只能配对：

- **配对规则**：一条 `buy_history` 订单配给一张我的单，要同时满足：`type=2`（求购成交）、同 `goods_id`、同价、订单建于这张单之后、没配给过别的事件。几张单都满足时配建单最早的那张。
- **交易中**：订单的 `state` 不是 `SUCCESS`，也不是 `FAIL`，并且配得上一张活跃的单 → 记 `in_trade_since`，推「交易中」（成交推送 spec §3.1 的同一套状态）。这个状态的真实取值还没见过，第一次见到时写进调研。
- **部分成交**：`real_num` 变多 → `filled` 事件（剩余件数 = `num − real_num`），和悠悠一样。
- **消失**（`gone`）：去最近的订单里配 `SUCCESS` → `outcome=done`，`outcome_at = transact_time`（精确），`order_event.outcome_ref` 记 BUFF 订单号（新列，防止一单配两次）；推「求购成交」。
- 配不到：下一轮再查一次（新订单可能晚到）。还配不到时，交易中出现过就记 `likely_done`（推测成交，不推，ADR-0018 同一口径），没出现过就记 `missing`（撤单），也不推。
- 一轮只看订单第 1 页（20 条）。一轮里成交超过 20 笔的情况不处理，等真碰到再说。

## 7. 推送

- BUFF 单**一律带简称**：`[BUFF] AK-47 | 翔鹤 (略有磨损)`。悠悠单的规则不变（悠悠号 ≥ 2 才带）。所以**只有一个悠悠号、外加 BUFF 时，悠悠的推送一个字不变**。
- 点击链接：BUFF 单跳 `https://buff.163.com/goods/<goods_id>`，悠悠单照旧。
- 「升到第 1 名」正文里 BUFF 单多一行「前面还有 N 张条件单」（N > 0 时）。
- 登录失效：`BUFF 登录已失效：<简称>`；访问受限：`BUFF 访问受限，已暂停 2 小时`。都按号、24 小时内只推一次。
- PushPlus 每小时 10 条的配额两边共用（`hourly_cap` 本来就是全局的）。BUFF 和悠悠的轮次分开推，不合并成一条。

## 8. 看板

- **总览**：BUFF 单和悠悠单在同一张表里。账号切换多一个「BUFF」。BUFF 行商品名后面带「BUFF」标签（启用的号 ≥ 2 时第一个号不带标签，这条规则不变）。名次一列：`cond_ahead > 0` 时提示「前面还有 3 张条件单」。在售价、价位建议两列在 BUFF 行显示「—」。
- **详情页**：同一个模板下挂着的 BUFF 单也列出来（带标签）；价格梯仍是悠悠的队列。`template_id < 0` 的单不链详情页。
- **系统页**：BUFF 号一张卡片，和悠悠的卡片同一个组件。按钮文字是「更新 cookie」；到期一栏显示「未知（BUFF 未提供）」，代替 token 到期。「添加账号」对话框先选平台（悠悠 / BUFF），选 BUFF 时说明怎么复制 `session`。
- **`/api/meta`**：`accounts[]` 每项加 `platform`；`service.issues` 加 `buff_paused`（访问受限暂停中）。
- **简报、选品、价位、市价提醒、分析**：只看悠悠号的单（查询加 `account_id in 悠悠号` 的条件）。这些地方现在用 `select(MyBuyOrder).where(active)` 查全部单，plan 里逐个改。

## 9. 给盈亏统计

盈亏那边（ADR-0025）要 BUFF 的买入、卖出、库存。BUFF 期提供数据，**配对逻辑、盈亏页由盈亏那边改**。

- 每天的盈亏任务里，对每个启用的 BUFF 号调 `sync_buff_trades(session, acc)`：
  - 卖出：`sell_history` 里 `state=SUCCESS` → `trade_order(platform='BUFF', side='sell', qty=1, amount=price, net_amount=income, net_exact=True, created_at=订单建单时间, finished_at=transact_time, asset_id=assetid)`。
  - 买入：`buy_history` 里 `state=SUCCESS`（`type` 2 求购、6 直接购买）→ `side='buy'`，`net_amount = amount`，时间同上。
  - **`hash_name` 必填** `goods_infos[goods_id].market_hash_name`，`name` 填中文名：跨平台配对按 `hash_name` 认同一件饰品，不按 `template_id`。`created_at` 是建单时间（先进先出比「卖出之前买的批次」用它），`finished_at` 是成交时间。
  - 增量（和悠悠 `services/pnl.py::sync_trades` 同一套，评审 2026-11-24）：列表按建单时间倒序、成交可能晚几天，**不能翻到已知单号就停**。日常同步翻到「不满一页」或「整页都是已知单」才停；首次导入（`import_all`）不看已知单，一直翻到空页（卖出约 4 页、买入约 2 页，每页 100 条）。`total_count` 不可信（调研 §9.1）。
  - `template_id` 按 §4 的映射；对不上的用 `-goods_id`。
  - `order_no` 用 BUFF 原订单号（`trade_order` 的唯一键是 `(platform, order_no)`，不用加前缀）。
- 库存：`fetch_buff_holdings(acc)` 返回 `[(market_hash_name, template_id, assetid)]`，盈亏那边决定怎么并进持仓。**注意**：BUFF 库存就是绑定的 Steam 账号的库存。悠悠号绑的如果是同一个 Steam 号，两边的库存是同一批货，按 `assetid` 去重。
- 出租：网页版拿不到（调研 §9.3），不做。
- 卖家、买家的身份信息不入库。

## 12. 测试

- **fixture**：用户登录状态下再做一次只读请求，把 `wait_supply`、队列（普通单、条件单混排的那个）、购买订单、卖出订单、库存各存一份，脱敏后（`user_id`、昵称、Steam ID、交易链接、头像全换掉）放 `tests/fixtures/buff/`。约 5 次请求。
- 适配器：字段解析、`Decimal`、对手信息不进数据类（断言 fixture 里的昵称不出现在任何数据类里）；五种错误码；429 + HTML；只有 GET。
- `core/buff_rank.py`：普通单在条件单后面、同价早晚、排除自己、条件单只和相同条件比、`cond_ahead`、翻页、找不到时的 `beyond`。
- 候选：`price ≥ buy_max_price` 优先、ALERTING 次之、轮换、上限。
- 同步：「消失」只在本号判（BUFF 号同步不碰悠悠单，反过来也一样）；改价；部分成交。
- 配对：同价同饰品两张单配建单早的；订单不重复配；配不到时 `likely_done` 和 `missing`；交易中。
- 推送：BUFF 单带 `[BUFF]`；一个悠悠号 + BUFF 时悠悠推送和现在逐字相同（扩展现有的单号快照测试）。
- 简报、选品、价位、市价提醒不含 BUFF 单。
- 盈亏导入：增量停在已知订单号、`net_exact`、只存 SUCCESS、对手信息不入库。
- 只有悠悠号时不注册 `buff_round`、不发 BUFF 请求。
- 迁移 0017 往返。
- 前端：账号切换含 BUFF、BUFF 标签、`cond_ahead` 文案、系统页 BUFF 卡片、添加对话框选平台。

## 13. 验收

1. 测试实例（verify-dashboard）：demo 里加一个 BUFF 号和几张单（含一张条件单、一张 `cond_ahead > 0` 的），总览、详情、系统页浅色、深色各看一遍。
2. 正式环境：用户在系统页添加 BUFF 号（粘 `session`）→ 第一轮后对照 BUFF 网页，核对 3 张单的名次和榜首价。
3. 跑一周：日志里 BUFF 有没有 429、验证码；`session` 多久失效；第一次真实成交时看交易中、成交推送对不对，把订单的 `state` / `progress` 取值补进调研。

## 14. 和 ADR-0022 的出入

- ADR 写的是「用 SteamDT 的 BUFF 最高求购预筛候选」。实测发现 `wait_supply` 每张单自带 `buy_max_price`，更准、不花 SteamDT 配额，改用它（§5）。ADR 同一个提交里补一句。
- ADR 写「遇到验证码或 429 就停 BUFF 通道」，这里具体成暂停 `pause_hours` 后自动恢复；暂停期间不重试。
