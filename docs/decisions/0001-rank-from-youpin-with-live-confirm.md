# 0001. 排名用悠悠上报的 rank，推送前用公开队列实时核对

- 日期：2026-09-06 定「用上报 rank」；2026-09-21 加「推送前实时核对」
- 状态：生效
- 拍板：补记（依据 research 文档与提交记录）

## 背景

原设计（spec 旧 §4）每轮给每张求购单各发一次匿名请求，在公开队列里数出自己的位置。真实账号 371 张单跑起来一轮要 18 分钟以上，比轮询周期还长。

同时发现 `searchPurchaseOrderList` 每行自带 `rank` 和子队列榜首价 `maxPurchasePrice`。2026-09-07 用三张单对照公开队列，查实 `rank` 就是同条件子队列排名（R1 要的语义）。

但 2026-09-21 查到上报值**会滞后几分钟**：模板 108753 悠悠说第 2 名、榜首 351，同一秒的公开队列是 352 / 351 / 我的 → 实际第 3 名。滞后最严重的恰好是有改价机器人的刀、高价皮肤队列。细节见 [悠悠对接记录 §5、§5.5](../research/2026-09-06-live-api-findings.md)。

## 决定

- 每轮 1 次认证请求同步全部单，**以上报 rank 为主数据**。
- 对「进了告警带、还没在告警中」的单，推送前用公开队列现算排名和榜首价，告警判断和推送文案都用实时值（`alerts.confirm_with_live_queue`，上限 `live_confirm_max`）。核对失败就退回上报值，绝不因此不告警。
- 匿名队列只有 20 行；装不下又没找到自己时，用认证请求深取（`polling.deep_page_size`）。
- 每轮抽样核对 5 张（pass B），作为 rank 语义变化的哨兵。

## 否决的方案

- 继续逐张单轮询公开队列：太慢，且请求量正是风控盯的量级。
- 完全信任上报值：滞后会让推送里的「榜首价」错在最值得抢的那些单上。

## 影响

- `services/monitor.py` 的每轮流程；快慢档调度作废，`MyBuyOrder.lane` / `last_rank` 成为死字段。
- 如果 `searchPurchaseOrderList` 哪天被移到 `sk` 加密通道后，这个决定失去基础，要重新评估。
