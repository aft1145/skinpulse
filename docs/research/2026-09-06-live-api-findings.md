## 1. 通道：App 通道已被版本闸门锁死，必须走 PC 通道

| 头部 | 主机 | 结果 |
|---|---|---|
| App 头 `App-Version: 5.28.3`（Steamauto 用的值） | api.youpin898.com | **HTTP 429 + code 85100「当前app版本过低」** |
| App 头改成 `5.26.0` | 同上 | **仍然 85100** |
| PC 头 (`platform=pc, appType=1, App-Version=5.26.0`) | pc-api.youpin898.com | ✅ code 0 |
| PC 头 | api.youpin898.com | ✅ code 0 —— **App 主机接受 PC 头** |

关键：闸门卡的**不只是版本号**，安卓通道要求一个真实的当前客户端版本，我们不知道是多少。PC 通道没有这个问题。

**诊断陷阱**：版本闸门返回的是 **HTTP 429 + body code 85100**。客户端若先看 429 就会报「限流」，把人引向完全错误的排查方向。`_handle_response` 已修正为：429 时若 body 有业务码，以业务码为准。

`skinpulse/adapters/youpin/client.py` 仍保留 `_app_headers()` 和 `[youpin.app_headers]` 配置，作为 PC 通道日后也被闸门盯上时的逃生舱，当前无人调用。

## 2. 登录：短信被滑块验证码挡死，只能贴 token

从网站 JS 包里挖出的完整错误码表（`umi.js`）：

```
success: 0            loginExpire: 84101      unBoundSteam: 2005
ABSENT: 1110201       EXPIRED: 1110202        SLIDER: 1110205
UPWARDSMS: 1110206    RECOVERY: 1110207       PROHIBITLOGIN: 1110208
```

**`1110205 = SLIDER`**：发短信前要求先过滑块验证。这是反自动化措施，不绕过。

PC 端登录接口（探明的请求格式，用非法值逐字段试探得出，全程未发出任何短信）：

- `POST /api/youpin/userAuth/smsLogin/sendSmsCode` — body `{sessionId, area, mobile}`
- `POST /api/youpin/userAuth/smsLogin/doLogin` — body `{sessionId, area, mobile, code, tenDayFreeSignIn, type:1}`
- `sessionId` 由客户端生成（uuid4 即可）

字段名坑：`mobile` 必须小写（`Mobile`/`phone` 全被忽略）；`sessionId` 必须驼峰（`SessionId` 不认）。

**补充（2026-09-24，Mac 上实测一次）**：这次 `sendSmsCode` **没有**要求滑块，短信真的发到了手机；但带着正确验证码调 `doLogin`，返回 `code -4`、`msg "Required request body is missing"`。说明 PC 站的 `doLogin` 现在要的 body 和上面记的不一样（可能换了字段或做了加密），未深究。结论不变：`login` 走不通，照旧用 `set-token`。别为了试它反复触发短信。

**扫码登录是死路**：`userAuth/scanCodeLogin/getQRCode?scene=1` 确实返回有效二维码（内容 `uuyp://url.uuyp.cn/...#/scanCodeLogin`），但**网页登录弹窗没有扫码入口，App 里也找不到扫一扫**。推测是给「上号器」之类的桌面工具用的内部流程。已验证此路不通，别再试。

### 实际可用的登录方式

浏览器正常登录（滑块由人来过）→ devtools → Network → 任一 `pc-api.youpin898.com` 请求 → 复制请求头 `authorization` 的值 → 看板「系统」页的「更新 token」（2026-09-27 起，立即生效）或 `set-token`（要重启服务才生效）。

- 值是一个 **JWT**（`eyJ0eXA...` 开头，约 316 字符），网页端发送时**不带 `Bearer ` 前缀**（我们的客户端加了前缀，服务器也接受）
- token 不在 `localStorage.LOGIN_TOKEN`（那是 App 内嵌网页的存储路径，桌面浏览器取到 null），在 cookie `uu_token` 里，但从请求头直接取更直接
- ~~实测有效期约 6 天~~ **更正（2026-09-23）：这个结论证据不足。** token 是 JWT，`exp` 字段就是到期时间，勾了「10天内免登录」时是签发后整 10 天（两个 token 都是如此）。当初只观察到第 1 天有效、两周后无效，真实失效时间没测到。以 JWT 的 `exp` 为准；当前 token 的 `exp` 是 2026-10-01 15:19，届时可以顺便测准。
- **同一个登录会话，token 不会续期（2026-09-27）**：用户在浏览器里重新复制了一次 authorization，粘进看板，校验通过，但 `exp` 还是原来那个（签发 + 10 天）。要拿到新的到期时间，得在浏览器里**退出再重新登录**。
- **同步四百多张求购单要 30～40 秒（2026-09-27 实测 39 秒）**：`searchPurchaseOrderList` 每页 40 张、共 11 页，页与页之间 `page_sleep_s = 2.5` 秒。所以网页换 token 不在请求里同步，改成让下一轮监控马上开始（每轮开头先同步）。
- **校验 token 只要一次 `getUserInfo`，一两秒**；网页换 token 的校验复用正在跑的 client 的设备身份（deviceId、uk），不多打 deviceW2。

## 3. 加密通道：`getUserInfoForApp` 不可用

`GET /api/youpin/bff/user/Account/getUserInfoForApp` 带上有效 token 后返回：

```
HTTP 200, content-type: application/json, sk 响应头存在, 1856~2208 字节十六进制密文
```

抓包显示客户端**请求头里也带一个 344 字符的 `sk`**，服务器才回密文——是客户端发起的加密通道。网页 JS 的响应拦截器里有对应分支：

```js
Le.headers && Le.headers.sk ? {sk: Le.headers.sk, data: Le} : ...
```

**复刻成本高且没必要**：`GET /api/user/Account/getUserInfo`（旧接口，app 主机，PC 头）返回同样的信息、明文 JSON、`Code:0`。当前代码用的是它。

> 风险提示：如果哪天 `searchPurchaseOrderList` 也被移到 `sk` 通道后面，整个项目会失去数据来源。届时要么复刻加密，要么退回轮询公开队列（匿名通道不受影响）。

## 4. `searchPurchaseOrderList`：真实字段名（推断几乎全错）

信封（已确认）：`{"code":0,"msg":"成功","timestamp":<int>,"data":[...]}` —— `data` 是**裸列表**。

每行 21 个字段：

```
isNew, orderNo, templateId, commodityName, iconUrl, unitPrice, styleSpecial,
abradeText, fadeText, buyQuantity, quantity, maxPurchasePrice, autoReceived,
rank, status, statusText, statusTextColor, createTime, countDownTime,
lastPriceUpdateTime, checkPriceMessage
```

| 我们原先猜的 | 真实 | 后果 |
|---|---|---|
| `purchasePrice` / `price` | **`unitPrice`**（字符串，如 `"24"`） | 几百张单价格全存成 `0.00` |
| `specialStyle` | **`styleSpecial`**（词序反的） | 款式条件丢失 |
| `surplusQuantity` | 不存在，用 `quantity - buyQuantity` | 剩余量恒为 1 |
| `purchaseNo` | **`orderNo`**（候选名单恰好蒙中） | — |
| `templateHashName` | **不存在** | — |
| `typeId` | **不存在**（公开队列里有） | 子队列键少一维 |

`maxPurchasePrice` 是带货币符号的展示串（`"¥28.1"`），`unitPrice` 是纯数字串。

**教训**：当时的守卫只检查 `purchase_no` 和 `template_id`，这两个恰好蒙对，于是同步报告「全部成功」而价格全是 0。守卫现已增加「价格必须 > 0」。**任何基于推断字段名的解析，守卫必须覆盖业务上不可能为空的字段。**

## 5. 最重要的发现：`rank` 和 `maxPurchasePrice` 是白送的

响应里直接带**我们自己的排名**（字符串，实测范围 1~213）和**当前榜首出价**。

三张单手工核对公开队列，悠悠的 `rank` 与观察到的位置完全吻合。**这把架构从「每张单每轮一次匿名请求」变成「每轮 1 次认证请求」**：

| | 旧设计 | 新设计 |
|---|---|---|
| 每轮请求 | 每张单 1 次匿名 | 1 次认证 + 5 次抽样 |
| 耗时 | 18.5 分钟（超过轮次周期，根本跑不完） | 约 20 秒 |

### `rank` 的语义（2026-09-07 已查实：**同条件子队列排名**）

> 本节 09-06 写的时候是「尚未确定」，当时的判断是「这个账号的数据里两种定义恰好重合，分不出来」。**这句话本身就是错的**——重合的只是那天手工核对的三张单。09-07 换了几张单一看，两种定义差得很远，而悠悠每次都站在子队列这边。

三张「磨损不限」的求购单，同时取回公开队列逐行数：

| 模板 | 全表位次 | 同条件（不限）子队列位次 | 悠悠 `rank` |
|---|---|---|---|
| 1022 裹手 | 18 | **4** | 4 |
| 60677 暗影双匕 | 4 | **3** | 3 |
| 47829 九头蛇手套 | 11 | **6** | 6 |

三次全中子队列，没有一次是全表。**`maxPurchasePrice` 同样是子队列榜首**：模板 1022 全表最高 332、子队列最高 276，悠悠给的是 276。

一个反面确认：如果「不限」被当成通配、能匹配任何磨损区间，那模板 1022 上面那 17 行都该计进去、`rank` 应该是 18。实际是 4，所以**「不限」是一个独立的条件值，只和别的「不限」单排在一起**——正是 `queue_key` 现在的做法。

**尚未验证的维度**：这三张单差异都只在磨损上。`styleSpecial`（款式）/`fadeText`（渐变）/`typeId` 这三维账号里没有对应的单子，仍然没有证据。抽样校验（pass B）因此保留，但它的角色变了：从「等着回答一个未知问题」变成「语义万一被改动时的哨兵」。

### 那两类分歧的下落

- **「裹手」（模板 1022）—— 结案，是我们的视野盲区，不是悠悠的问题**。09-07 复现时它排在全表第 18、子队列第 4，两边一致。之前 5 次算不出排名，是因为它当时排在全表 20 名开外，而公开队列一页只返 20 行（`total=24`、返 20 行、`hasNext` 还谎报 `false`），我们根本看不见自己那行。09-06 那次「子队列只剩 1~4 行且找不到自己」的推断——`queue_key` 把它过滤掉了——是错的：过滤是对的，只是那 4 行里本来就不该有我们。
  **已改**：这种「页取满了却找不到自己」的情况现在单独判成 `inconclusive`，不再计入不一致，见 `core/rank.py::verification_outcome`。
- **「廓尔喀刀」—— 2026-09-21 结案：悠悠的 `rank` 不是实时算的**，见 §5.5。09-06 那条「像是有一行悠悠不计数」的直觉方向是对的，只是原因不是「不计数」，而是「还没看见」。

## 5.5 `rank` / `maxPurchasePrice` 有几分钟的滞后（2026-09-21 查清）

09-06 记下的那条「廓尔喀刀稳定差 1，像是有一行悠悠不计数」，现在有答案了：**悠悠给的 `rank` 和 `maxPurchasePrice` 不是实时算的，它落后公开队列几分钟。**

模板 108753：

```
悠悠（searchPurchaseOrderList）：rank=2，maxPurchasePrice=¥351
同一秒的公开队列：352（建单 2026-09-21） / 351（建单 2026-09-14） / 我的单（低得多）
                                      → 实际第 3 名
```

排除法走完了：

1. **不是隐藏条件**。把公开队列的原始 JSON 整行打出来逐字段比对，被漏掉那一行的 `abradeText`/`fadeText`/`specialStyle`/`typeId`/`purchaseLabelList` 与其它行完全相同，没有任何字段能把它区分出来。
2. **不是采样间隔造成的**。认证接口和公开队列背靠背连采三轮（间隔 2 秒，跨 100 秒），两个模板的差异分毫不动。
3. **确实是滞后，不是冻结**。同一张单上，09-14 那个自动改价机器人把价格从 248 改到 351 之后，悠悠给的 `maxPurchasePrice` 在十分钟内从 248 跟到了 351——只是始终没算进当天新挂的那一行。

滞后最严重的正是有自动改价机器人的队列（刀、高价皮肤），也就是最值得抢的那些。

**影响**：告警原本完全建在这个值上。现在会在推送之前给「即将告警」的那几张单用公开队列现算一遍排名和榜首价（`alerts.confirm_with_live_queue`，见使用手册（docs/guide.md））。pass B 的抽样核对也因此获得新的解读：**它报出来的不一致，多数是在指认这个滞后，而不是语义分歧**。

## 6. 其它零散事实

- **空响应 = 轻度限流**。短时间内连续约 10 次请求会出现 1 次空 body。它会被映射成 `RateLimited`，容易被误读成 token 无效。`set-token`/`probe-token` 已加 3 次重试。
- 排除项（对着真机 token 实测）：token 截断、中间插空格、每 50 字符折行、结尾 `\r`/制表符、零宽空格 —— **全部返回干净的 84101 或客户端 `LocalProtocolError`，都不会产生空响应**。
- `queryOnSaleCommodityList`（匿名）返回深度**因模板而异**：templateId 1414 只返 1 行，34966 返 10 行。不能依赖它做在售深度。
- 它的 **`pageSize` 同样被忽略**（2026-09-21 实测，templateId 54882 传 5/10/20/50 一律返 20 条），跟公开求购队列是一个毛病。所以代码里不给它配可调页大小——只取最低价，返多少条都够用。
- **返回 0 条是一个确定的结论**，不是失败：templateId 59284（SSG 08 StatTrak™ | 巨铁 破损不堪）连查三次都是 0 条，用户在网页上核对过确实无人在售，而同一皮肤换个磨损有人挂。因此 `sell_depth=0`（没人卖）和 `sell_depth=NULL`（没查到）必须分开存，见 `MyBuyOrder` 的注释。
- 匿名公开求购队列固定只返前 20 条，`pageIndex`/`pageSize` 被忽略。**登录后两个参数都真的生效**（2026-09-21 实测，模板 101422，`total=347`）：

  | 请求 | 返回 |
  |---|---|
  | 匿名 `pageSize=100` | 20 条 |
  | 登录 `pageSize=100` | 100 条 |
  | 登录 `pageSize=400` | 347 条（全部） |
  | 登录 `pageIndex=2, pageSize=20` | 20 条，与第 1 页单号**零重叠**，正好接在第 20 条之后 |

  代价是这得用账号通道，风控盯的正是账号，所以只在"匿名那页装满了又没找到自己"时才升级（`polling.deep_page_size`）。
- **匿名公开求购队列会被打出 HTTP 403（2026-11-24）**：一次性脚本按 3～4.5 秒一个、不同模板连查，第 78 次起一律回 HTTP 403（不是业务码），正式服务每轮的 5 次抽样也跟着失败，至少持续约 50 分钟（14:39 服务停下前一直 403，18:07 再起来时已正常）。服务把这个 403 当普通错误：不暂停匿名通道，告警前的实时核对失败时退回悠悠上报的名次，照常告警。同一时段在售接口连查 126 次都正常。这个接口一口气别查几十个模板；要大面积看榜首，先用「我的求购」列表里白送的 `maxPurchasePrice`（暂停单 intent（未公开））。
- 更坑的是 **`hasNext` 会谎报**：模板 1022 实测 `total: 24`、只返 20 行、`hasNext: false`。想判断有没有被截断，只能拿 `len(rows)` 和 `visible_limit` 比，或者看 `total`，不能信 `hasNext`。
- **求购成交后，这张单直接从 `searchPurchaseOrderList` 里消失**（09-07 实测：一张 24 元的格洛克成交，下一轮同步总数就少了 1）。同步逻辑按 `active` 处理，不会报错，但这意味着「单子数量减少」本身是个正常事件，不该当成同步异常。

## 7. 求购单的状态和 `rank = "*"`（2026-10-02 实测）

起因：09-29 到 10-02 有 4 张单成交却没收到推送（见 求购成交推送 intent（未公开））。用 `searchPurchaseOrderList` 换 `status` 只读探测了一次（约 30 个请求，2 秒一个）：

| status | statusText | 说明 |
|---|---|---|
| 20 | 求购中 | 现在同步用的就是这个 |
| 30 | 暂停中 | **求购余额不够时，悠悠自动把单子暂停**，不是删除。一单成交扣款后，十几张刀和手套在下一轮从 20 里消失，全在这里。当时有几百条（读到第 7 页还没完） |
| 40 | 已完成 | 成交的单。`buyQuantity` 是买到的件数，`createTime` 变成**成交时间**（4 张都和用户说的时间对得上，到秒） |
| 10、21、25、35、41、45、50、60、70、80、90、100、0、-1 | — | 都是 0 条 |

- **30、40 的列表不是按时间排的**：`pageSize=20` 的第 1 页里没有 09-30 成交的梦魇武器箱，`pageSize=40` 的第 1 页里有。要确认某张单的去向，只能按单号一页页找，不能只看第一页。
- 字段和 20 一样（`orderNo`、`unitPrice`、`quantity`、`buyQuantity`、`rank`、`createTime`……），30 和 40 的 `rank` 都是 null。
- **`rank = "*"` 是「交易中」**：有卖家卖给了这张单、交易还没完成。库里出现过的两次（CZ75 短趾雕 09-29，`*` 约 15 分钟；AWP 树蝰 10-01，17:49 到 18:16 约 27 分钟）都以成交结束。这期间 `maxPurchasePrice` 不再算自己这张，`createTime` 变成被卖的时刻（AWP 是 17:49:49）。用户确认：17:49 就是被卖的时刻，求购余额当时就扣了，所以那 19 张单马上被暂停。`_parse_reported_rank` 现在把 `*` 当成「没有名次」。
- **补充（2026-11-23）：改价时旧单也会短暂显示 `*`**。沙漠之鹰 | 玛珀丽（崭新）53 → 50 改价，16:52 那轮旧单 `rank = "*"`、`createTime` 还是建单时间，16:56 那轮旧单消失、新单出现。真被卖时 `createTime` 会变成被卖的时刻（10-02 以来 9 张真成交都是），所以用「`createTime` 变没变」区分（intent（未公开））。同一天还有一张纪念包真成交了，却**不在「已完成」里，其余所有 status 也没有**，只能记「推测成交」。
